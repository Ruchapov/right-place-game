## Architecture

### Server (server/src/)

| Endpoint | Body | Description |
|---|---|---|
| `POST /run/start` | — | Spend energy, generate 3 rooms, save currentRun |
| `POST /run/room` | — | Process chest/trap |
| `POST /run/battle-result` | `{won, damageTaken, damageDealt, skillUses, actualHpLost, potionsUsed}` | After fight |
| `POST /run/smuggler-result` | `{exchange: bool}` | Smuggler choice |
| `POST /run/puzzle` | — | Get puzzle question |
| `POST /run/puzzle-result` | `{selectedIndex}` | Submit puzzle answer |
| `POST /character/skills` | `{skills: string[]}` | Save equipped skills (max 2) |
| `POST /character/buy-potion` | — | Buy 1 potion for 20 gold |

**Prisma Character fields:**
`level, energy, endurance, strength, agility, luck, gold, trophies, crystals, potionCharges, totalDamageReceived, totalDamageDealt, totalSkillUses, strengthAtLevelUp, enduranceAtLevelUp, equippedSkills([]), currentRun(Json?)`

**`currentRun` shape:** `{ rooms, index, hp, potions, puzzleId? }`

### Frontend (src/)

**`Battle.tsx`** — PixiJS v8 fullscreen combat.
Props: `{initialHp, maxHp, isBoss?, level?, equippedSkills?, potionCharges?, strength?, onBattleEnd}`

**⚠️ Спрайты игрока — УСТАРЕВШИЙ раздел, см. "Art & Animation Pipeline" ниже.**
Старые заглушки (Walk.png 8 кадров 128×128 и т.д.) заменены полным набором
анимаций героя и первого врага, ещё не подключённым к коду. Секция ниже
оставлена как есть до момента интеграции нового набора в Battle.tsx.

**Координаты в Battle.tsx:**
- FLOOR_Y = height - 200
- player.y = FLOOR_Y (anchor = 0.5, 1 — ногами на полу)
- enemy.y = FLOOR_Y - ENEMY_H + 40
- WORLD_WIDTH = 3000, камера следует за игроком

**Анимации игрока (реализовано в коде на момент последней проверки):**
- idle: idleFrames, speed 0.15, когда стоит
- walk: walkFrames, speed 0.3, когда движется
- attack: attackFrames, speed 0.4, один раз при нажатии ⚔, потом возврат к idle/walk
- Флип: scale.x отрицательный = смотрит влево, положительный = вправо

**Параллакс в ticker:**
- bgSky.tilePosition.x = -cameraX * 0.1
- bgRuins.tilePosition.x = -cameraX * 0.3
- platform.tilePosition.x = -cameraX

**`App.tsx`** — Main state.
PlayerData: `{id, firstName, level, gold, trophies, strength, endurance, agility, equippedSkills, potionCharges}`
- Navigation: 5-tab bottom nav (Персонаж / Магазин / Исследовать / Снаряжение / Друзья)
- Run flow: Start → showRoomIntro(2s) → enterCurrentRoomDirect → auto-next → results screen

## Art & Animation Pipeline (НОВОЕ — готово, ждёт интеграции в код)

### Пайплайн (проверенный, воспроизводимый)
```
1. ДИЗАЙН: Nano Banana Pro (Google Flow) → референс-арт персонажа,
   строго вид сбоку ("side view profile, facing right/left"), плашка сзади.
2. АНИМАЦИЯ: Veo (через Flow) → видео 4с/24fps по 4-блочному скелету промпта:
   a) вид сбоку + статичная камера + "never turns toward camera"
   b) кадрирование (wide framing, full body, never touches frame borders)
   c) ДЕЙСТВИЕ — единственный блок, который меняется между анимациями;
      описывать ГЕОМЕТРИЮ движения (что сгибается, куда смещается),
      НЕ эмоцию ("flinches" → модель рисует морду, а не тело)
   d) "Only the character on a flat gray background. No ground, no shadow,
      no dust, no effects" — жёсткий запрет вспышек/пыли/колец на ударе
3. НАРЕЗКА: ffmpeg → кадры → Python (PIL + scipy.ndimage) →
   удаление фона, поиск петли цикла, сборка спрайт-листа + PNG по кадрам.
```
Инструменты нарезки — одноразовые Python-скрипты в чате (не в репо), логика
описана ниже на случай повтора процесса для новых персонажей/анимаций.

### Известные грабли пайплайна (не наступать повторно)
- **Veo даёт секунды статики в начале** видео перед началом действия —
  всегда резать по скачку "движения между кадрами" (diff масок), а не брать
  видео от 1 кадра.
- **Слова "hit/strike/blow/dies/fatal"** триггерят фильтр Flow как опасный
  контент. Обход: переформулировать как физическое состояние без источника
  ("is exhausted and loses his strength" вместо "takes a fatal blow").
- **Модель дорисовывает эффекты, если в тексте есть "причина"** (получил
  удар → чем-то ударили → рисует снаряд/вспышку). Решение — убрать саму
  причину из промпта ("nothing touches it", "there is no ground beneath
  him"), а не только запрещать эффект.
- **Композиция против водяного знака**: знак Flow всегда в правом нижнем
  углу кадра. Если персонаж длинный (четвероногий, лежащий) и дотягивается
  до знака — они сливаются в один объект при вырезании фона. Фикс:
  в промпте явно просить "small in the frame, positioned in the upper
  left, large empty space in the bottom right corner" — тогда знак остаётся
  на пустом фоне и вырезается сам как отдельный компонент.
- **Заливка дыр (binary_fill_holes) не должна быть безусловной**: если
  заливать ВСЕ дыры в силуэте, крупные проймы (между рукой и телом, между
  ног) закрашиваются фоновым серым и остаются видимыми пятнами в игре на
  цветном фоне. Правильно — заливать только мелкие дыры (< ~400 px,
  артефакты контура), крупные оставлять прозрачными.
- **Выравнивание кадров по ступням годится ТОЛЬКО для кадров, сгенерированных
  по отдельности** (напр. спрайт-лист Nano Banana, где персонаж каждый раз
  в новом месте клетки). Для кадров, вытащенных из ОДНОГО видео со статичной
  камерой — кадры уже согласованы между собой; выравнивание по ступням
  каждого кадра отдельно портит анимацию (перса начинает трясти), т.к. якорь
  «ступни» гуляет из-за плаща/лапы/меча внизу силуэта. Правильно: резать все
  кадры одной анимации ОДНИМ неподвижным окном.
- **Между анимациями одного персонажа** (idle/attack/hurt и т.п.) якорь
  нельзя брать по ступням наивно — если в одной из анимаций конечность
  выносится далеко (бросок лапой, выпад мечом), медиана ступней уезжает и
  персонаж прыгает при смене состояния в движке. Правильно — совмещать
  анимации между собой по IoU-наложению силуэтов первого кадра с базовой
  (idle), а не по ступням.
- **Фон не всегда получается чисто зелёным** — иногда Veo даёт зеленовато-
  серый (менее насыщенный) или вообще серый фон (если в промпте забыто
  слово "green"). Простой порог `g > r+15 and g > b+15` в таком случае не
  добирает до alpha=0 в углах (остаётся дымка ~40-50 альфы). Надёжнее:
  сэмплировать РЕАЛЬНЫЙ цвет фона из угла КАЖДОГО кадра и вырезать по
  Евклидову расстоянию до него, а не по фиксированной "зелёности".
- **Разные анимации одного перса, снятые разными роликами Veo, не обязаны
  давать одинаковый bbox** — если в одной анимации конечность вылетает
  далеко за пределы позы из другой (напр. замах когтями шире, чем поза
  Idle), нельзя силой сажать оба в одинаковый квадратный холст: тело либо
  сожмётся мельче на кадрах с широким жестом, либо обрежется. Решение —
  единый МАСШТАБ пикселей (тот же коэффициент src→output, что и у Idle),
  но собственный (более широкий) холст под конкретную анимацию — как уже
  делали для Dash Strike героя (240×128 вместо 128×128).
- **Veo иногда разворачивает персонажа на 180° по горизонтали** несмотря на
  прямой запрет "keep facing direction", причём непредсказуемо — то в
  середине ролика на "активном" глаголе (rears back, атака), то сразу с
  первого кадра. Разворот ловится численно: найти на исходном референсе
  устойчивый асимметричный признак (напр. светящийся глаз) и сравнить его
  положение (% от края bbox) между роликами. Если только силуэт развернут,
  а само движение (напр. замах) логично относительно новой стороны —
  чинится зеркалом (`FLIP_LEFT_RIGHT`) при нарезке. Если же движение
  внутри ролика само по себе идёт "не в ту сторону от головы" (лапа бьёт
  НАЗАД от направления взгляда) — это не лечится зеркалом (оно перевернёт
  и голову, и лапу вместе, сохранив их неверное соотношение) — нужна
  перегенерация с явным "arm moves in the direction the head is facing".
  **Важно:** прежде чем чинить зеркалом — спросить у Андрея, видит ли ОН
  разворот на своём экране. Одного численного анализа недостаточно для
  решения переделывать готовый ролик.
- **"front-facing" и "profile/side-view" в одном промпте — противоречие.**
  Модель может послушать "front-facing" и развернуть персонажа лицом в
  камеру. Для строгого вида сбоку — только "strict side-view profile",
  без слова "front-facing" рядом.
- **Зум-наезд в первые ~5-10% ролика** — отдельный (от разворота) артефакт:
  Veo иногда "наезжает" от уменьшенного кадра до полного масштаба в первые
  8-10 кадров, даже при явном "no zoom" и стартовом изображении-референсе.
  Лечится не перегенерацией, а обрезкой этих кадров при нарезке — ищется
  кадр, где bbox стабилизируется (перестаёт расти), и нарезка начинается
  с него.
- **Референс-изображение "в упор" (объект во весь кадр) провоцирует Veo
  рисовать ещё крупнее и обрезать края.** Перед генерацией видео стоит
  всегда делать "отдалённый" референс-кадр: объект/персонаж на ~35-60%
  высоты холста 1920×1080, с полями со всех сторон, тем же зелёным фоном.
  Правильную долю (35% / 48% / 58% / 62%...) иногда приходится подбирать
  по обратной связи ("сильно отдалил" / "не влезает") — единого числа нет,
  зависит от пропорций объекта.
- **Копирайт-фильтр Google может сработать на силуэт, похожий на чужую IP**
  ("не могу создать видео из-за интересов сторонних поставщиков контента").
  Так сработало на дизайн NPC (сутулая фигура в капюшоне с 2 светящимися
  точками-глазами → похоже на Джаву из Star Wars). Обход — не переделывать
  дизайн полностью, а увести силуэт подальше (рост, форма капюшона,
  асимметричные/другой формы глаза) ИЛИ просто попробовать другой,
  более короткий промпт для видео с тем же PNG (иногда помогает).
- **Зелёный VFX-эффект на зелёном хромакее — плохая идея** (Heal-аура).
  Для таких случаев — чёрный фон + альфа = яркость пикселя (аддитивный
  ключ), а не хромакей по цвету.
- **Обычный экшн-глагол типа "rears back"** может сам по себе читаться как
  "поворачивается" — безопаснее описывать голой геометрией конечности
  ("pulls arm back behind itself"), а не позой всего тела.
- **Тень персонажа отличается от фона всего на ~10-40 по яркости** (почти
  тот же серый), а капюшон/тёмная одежда — на ~70-80. Фильтр "убрать тень
  по разнице с фоном" должен захватывать диапазон (-42..-6), а не любой
  тёмный объект, и применяться ТОЛЬКО к нижней трети кадра — иначе съедает
  тёмные детали костюма (было: капюшон героя лысел в анимации урона).
- **ПРАВИЛО ШИРОКИХ АНИМАЦИЙ**: если персонаж широко машет (руки/меч/выпад),
  кадры собирать на своей ШИРОКОЙ клетке с телом ПО ЦЕНТРУ. Иначе при anchor
  0.5 силуэт обрезается или "улетает" вбок при смене кадра. Так пересобран
  hurt героя (315px шириной вместо 379 у idle/run/attack). ИСКЛЮЧЕНИЕ —
  death: там покадрово НЕ центрируем, падение вбок — часть анимации, не баг.
- **Позиция спрайта в движке завязана на anchor (0.5, 1.0)**:
  `heroSprite.x = centerX бокса`, `heroSprite.y = низ бокса`. Из-за этого
  менять `anchor.x` покадрово НЕЛЬЗЯ (даже если кажется, что так проще
  подогнать смещённый силуэт) — это уводит картинку вбок относительно
  бокса-хитбокса, а не чинит проблему (пробовали на hurt, откатили).
- **Пиксельность/дрожь спрайта в движке** — это НЕ грабля самого арт-пайплайна
  (Nano Banana/Veo/вырезка), а рендер-настройка Pixi: недосэмплирование при
  сильном ужатии текстуры + низкое `resolution` канваса. Фикс — оба сразу:
  `resolution: Math.min(devicePixelRatio, 2)` + `autoDensity: true` на
  `app.init`, И исходник близко по размеру к размеру отрисовки (не 512→140px,
  а 288→140px — см. "Спрайты героя" в разделе Explore).
- **Референс и ролики для Veo — ВСЕГДА на ярко-зелёном фоне** (слово GREEN в
  промпте обязательно; без него Veo даёт серый фон, который плохо режется).
  Референс на зелёном генерить СРАЗУ в Nano Banana, не перекрашивать серый
  готовый арт в зелёный постфактум (даёт паразитную зелёную кайму по контуру).
- **Хвост Veo рисует по-разному в каждом ролике** — все анимации одного
  персонажа с хвостом/длинным придатком надо генерить так, чтобы хвост
  целиком помещался в кадр, и резать в достаточно широкую/ЕДИНУЮ клетку на
  все анимации сразу — иначе хвост не совпадает по месту между roll'ами.
  Эталон хвоста для сверки — walk (там он заметнее всего).
- **Вырезка по зелёному — despill, а не только alpha**: `G = min(G, max(R,B))`
  убирает зелёный "отсвет" на краях силуэта, который порог по alpha не ловит.
  Заливку щелей на спине/между шипами делать ТОЛЬКО в верхних ~60% силуэта
  цветом соседних пикселей — если заливать весь силуэт, получаются: а)
  чёрные просветы на спине на тёмном фоне игры, б) серые пятна в проймах
  между ног.
- **Единая посадка всех анимаций одного персонажа** — самый надёжный способ
  избежать "прыжка" при переключении между ними: одна клетка + голова в
  фиксированной точке (напр. X=130) + ноги на фиксированной линии (напр.
  Y=280) + один и тот же масштаб (высота существа ~243px в клетке 288px).
  Выравнивать по ГОЛОВЕ (стабильный ориентир между кадрами и анимациями), а
  НЕ по "торс-полосе" (шумит от дыхания/наклона) и НЕ по хвосту/лапам (гуляют
  сильнее всего именно они — см. граблю про хвост выше).
- **Дыхательный idle собирать ПИНГ-ПОНГОМ** (полдыхания вперёд + оно же назад
  в кадрах) — иначе на стыке последний→первый кадр виден шов петли. Для
  плавности не жалеть кадров (idle зверя — 24, walk — 16).
- **Death — падение НЕ центрировать покадрово** (смещение тела по ходу
  анимации — часть самого падения, а не баг верстки кадров, см. граблю
  "ПРАВИЛО ШИРОКИХ АНИМАЦИЙ" выше). Выравнивать по клетке нужно ТОЛЬКО
  входной кадр (стартовую стойку) по голове/ногам — остальные кадры кладутся
  в ту же клетку как есть.
- **Цвет между разными генерациями Veo отличается** (один и тот же
  персонаж в разных роликах может быть чуть теплее/холоднее/темнее) —
  приводить все анимации к цвету эталона (обычно idle) гистограммным
  совмещением ПО КАНАЛАМ (R/G/B по отдельности), а не по среднему цвету —
  среднее маскирует сдвиг и не выравнивает реально.
- **Проверять КАЖДУЮ анимацию GIF'ом на тёмном фоне игры на РЕАЛЬНОЙ
  скорости** (не на скорости просмотра/покадрово) до интеграции в код —
  на статичном кадре или медленном превью артефакты цвета/шва/тайминга
  часто незаметны, а на боевой скорости бросаются в глаза сразу.
- **Разъехавшийся якорь между анимациями = прыжок спрайта.** Даже при
  одинаковом масштабе и одной высоте клетки анимации прыгают, если центр
  головы у них на разном X (было: idle 198, hurt 138, jump 152 — разброс
  60px). Лечится пересборкой ВСЕХ анимаций персонажа в одну общую клетку
  с одним якорем (голова по X + ноги по Y), а не подгонкой по одной.
- **Кадры одного ролика нельзя выравнивать покадрово.** Якорь "верх
  силуэта"/"центр головы" гуляет между кадрами (капюшон, шарф, колено) и
  даёт мелькание/тряску. Кадры из ОДНОГО видео сажать ОДНИМ окном:
  единый масштаб + единый сдвиг на всю анимацию.
- **Персонажа в клетке центрировать, не прижимать к якорю idle.** Если
  тело сдвинуть вбок (напр. голова на X=178 в клетке 379), длинный плащ
  спринта вылезает за край и обрезается — обрезанный плащ читается как
  "плащ спереди". Сначала считать габариты силуэта, потом выбирать ширину
  клетки.
- **Despill применять ТОЛЬКО к зелёным пикселям, не ко всему силуэту.**
  G=min(G,max(R,B)) по всему телу утаскивает оливковые ткани в серый
  (было: 8.7% пикселей просели до -56 по зелёному). Правильно — despill
  только там, где G заметно больше R и B.
- **Гистограммное совмещение цвета к другому ролику — опасно.** Попытка
  подогнать цвет нового ролика под старый эталон по каналам дала зелёный
  отлив на тёмном плаще. Если Андрей просит не менять цвет — отдавать
  RGB ролика как есть (байт в байт), править только альфу.
- **Бинаризация альфы порогом даёт "крапинку" на тёмных участках.**
  Тёмный капюшон местами не добирает до порога и становится дырявым.
  Нужна заливка мелких дыр (< ~600px) внутри силуэта; крупные проймы
  (между ног, рука-тело) оставлять открытыми.

### Грабли арт-пайплайна — дополнения (выстраданы на боссе)

**Хромакей (итоговый конвейер вырезки):**
1. Цвет фона — медиана по 4 углам КАЖДОГО кадра.
2. **Альфа считается кейером по зелени**, а НЕ по евклидовой дистанции до фона:
   `α = 1 − (G − max(R,B)) / (то же у фона)`. Дистанция завышает α для светлых
   полупрозрачных элементов (следы, дым) — они остаются зелёными.
3. Цвет восстанавливать размериванием: `C = (наблюдаемый − (1−α)·фон) / α`.
4. **Замена цвета на «ближайший чистый» — ТОЛЬКО в полосе ≤4px от края.** Если гонять
   по всему телу, внутренние детали (зубы, язык) перекрашиваются в цвет соседей —
   пятна. Именно так я испортил пасть, а потом «лечил» её перекраской — двойная ошибка.
5. **Зелёные зоны в глубине тела** (фон виден сквозь раскрытую пасть) — заливать
   **фиксированным** тёмным цветом глотки с мягким краем. Фиксированный = одинаковый
   на всех кадрах = без мерцания.
6. **despill-формула `G=min(G,max(R,B))` на ВСЮ заливку запрещена** — краевой пиксель
   (смесь зелёного фона с тёмным контуром) превращается в тёмную бирюзу. Внутри тела
   формула безопасна.
7. Ужатие — **только с premultiplied alpha** (premultiply → Lanczos → unpremultiply).
   Без этого цвет прозрачной зоны затекает в край и создаёт светлую кайму заново,
   сколько маску ни чисти.
8. Заливать **только мелкие** дыры. Крупные проёмы (между лап) заливать нельзя —
   станут чёрным клином. Исключение: **верхние ~55% силуэта** (пасть) — там порог дыр
   поднимать до ~9000px, иначе раскрытая пасть мигает дырой на фон.
9. Порядок: угрозы → потом отсев отвалившихся островков. Наоборот — угрозы наречет
   новые обрывки прядей, и они повиснут точками вокруг силуэта.

**VFX (следы, дуги, пыль):**
- Тело — **жёсткий край**; VFX — мягкая альфа. Смешивать нельзя: мягкая альфа на теле
  = светлая кайма по контуру.
- VFX отделяется по **удалённости от силуэта** (>3px). Пиксели вплотную к телу к VFX
  не относить — иначе белая кайма вокруг персонажа.
- **Когда VFX пересекает тело** (дуга проходит сквозь руку/ноги) — правильного
  однослойного решения НЕТ: либо тёмные пятна в дуге, либо разрезанные конечности.
  Решение — генерить ролик БЕЗ эффекта и класть эффект отдельным ассетом.
- Пыль/дым можно сохранить как полупрозрачный слой — тогда нет дыр и черноты в местах,
  где эффект лёг поверх тела.

**Никаких правок «поверх» вырезки:**
- **Любая покадровая перекраска «по ближайшему» даёт рябь** — источник замены меняется
  от кадра к кадру. Внутрь силуэта не лезть вообще.
- Заморозка детали (перенос морды с опорного кадра) работает только при чистом
  СОВПАДЕНИИ. Если голова есть и поворачивается — лезет призрак старого лица.
  При вклейке менять **только цвет**, альфу не трогать (иначе куски висят в воздухе).
- Временное сглаживание по соседним кадрам мылит деталь и проблему не решает.

**Промпты Veo — что реально работает:**
- **Дрожание рисунка обработкой не лечится, только промптом.** Если Veo каждый кадр
  перерисовывает деталь (челюсть), нужен прямой запрет: «jaw stays completely still,
  the mouth keeps exactly the same shape, the face does not move».
- **Прилагательные веса («heavy», «powerful») в описании атаки Veo отыгрывает как
  подготовительную фазу** (лишний замах двумя руками), а не как вес удара. Нужна
  скорость — писать «quick», вес добиваться позой.
- **Скорость и амплитуды разводить как отдельные параметры**: «quick but small».
  Одним словом получается либо рывок, либо вяло.
- **Ускорять анимацию прореживанием кадров нельзя** — рябь. Медленный ролик =
  перегенерация, а не каждый второй кадр.
- **Перечислять детали дизайна вредно**: подробный список брони модель понимает как
  «дорисовать больше». Работает короткое «looks exactly like the reference image in
  every frame — nothing added, nothing removed».
- **Убирать причину, а не запрещать следствие**: «throws» тянет за собой предмет в
  руке, «slams onto the ground» — пыль. Помогает описывать голую геометрию движения
  («swings its arm forward at waist height») и «nothing below it, empty space».
- **Длинный промпт = длинное действие** (лишние повторы). Для одиночного движения —
  3–5 строк и явное «only ONE, it must not repeat».
- **Циклы (walk/idle)**: период искать **перебором пар начало-конец**, а не «ближайшим
  к нулевому кадру». Проверять глаз числом относительно среднего шага (цель <1.0).
- **Отдалённый референс обязателен**: объект «в упор» заставляет Veo наезжать и резать
  край. Для босса 50% высоты холста, для мелких объектов ~25% ширины.

**Проверка результата:**
- Смотреть **ВСЕ кадры теркой**, а не 5–7 выборочных. Половина ошибок пряталась именно
  в непроверенных кадрах.
- **Числовые метрики врут** — дважды показывали «улучшение» там, где глаз видел брак,
  и «без изменений» там, где стало хорошо. Приёмка только визуальная.
- **Превью-GIF собирать с ЕДИНОЙ палитрой** на все кадры (MEDIANCUT по склеенным
  кадрам). `ADAPTIVE` на каждый кадр = цвета плавают = ложная «рябь», которой в PNG нет.
- Переделанные файлы отдавать **под новым именем** — иначе кеш показывает старую версию.
- **Veo меняет отдалённость камеры между роликами** — заявленный единый масштаб
  персонажа между листами НЕ гарантирован, даже если так написано в README набора.
  Проверять обязательно. Численные метрики масштаба ВРУТ: высота силуэта завышена
  вытянутыми лапами и дугами удара, площадь занижена ракурсом, ширина головы зависит
  от поворота — все три давали разные ответы на одном наборе. Единственный рабочий
  способ — временный тюнер с полистовым множителем масштаба, разработчик подгоняет
  глазами по голове. Итоговые множители босса: melee ×1.08, melee2 ×1.20, death ×1.08
  поверх нормализации по ширине головы.

**Грабли, выстраданные на сцене "убежище" (герой у костра, вкладка Исследовать):**
- **Исходник для Veo делать СРАЗУ в 16:9 (1280×720).** Квадратный исходник Veo
  вписывает в широкий кадр обрезкой — у костра срезало языки пламени в 81
  кадре из 96.
- **Veo обесцвечивает персонажа относительно эталона.** Лечится не перекраской
  на глаз, а замером среднего и разброса по цветовым каналам на пикселях
  персонажа и переносом статистики с эталонной картинки (коррекция по
  каналам, не по общему тону). У героя коэффициенты вышли 1.61 / 1.40 / 1.20
  по R/G/B.
- **Ширина спрайт-листа не должна превышать 4096px** — предел текстур
  мобильных GPU. Если кадров много (герой — 24), раскладывать СЕТКОЙ
  (6 колонок × 4 ряда), а не одним длинным рядом.
- **Отрицательный z-index уводит элемент ЗА фон родителя**, а не «между фоном
  и контентом», как может показаться. Фон нужно выносить отдельным слоем с
  явным неотрицательным `zIndex` (0), а не пытаться просунуть контент под
  него отрицательным индексом.
- **Линейная анимация `background-position` НЕ сглаживает спрайт-лист** —
  вместо смены кадров получается непрерывный сдвиг картинки вбок (кадры
  "едут", а не переключаются). Спрайт-листы анимировать только `steps()`.
- **Плавность анимации задаётся частотой кадров (числом кадров в исходнике),
  а не длительностью CSS-анимации.** Длительность меняет только скорость
  прохода по уже существующим кадрам, но не добавляет промежуточных поз —
  «дёрганость» лечится перегенерацией с большим числом кадров, не тюнингом
  секунд.

- **Strength**: normalized dmg dealt / (1+0.18×(lvl-1)). +1 per 150 (until Str=20), then +1 per 350

- **Method 1**: +3 Endurance OR +6 Strength since last level-up
- **Method 2**: boss kill → instant +1 level


  (−20% maxHp) на кадре `CHEST_TRAP_STRIKE_FRAME=5`, неизбежен, без i-frames.
- Завершение: `stop()+gotoAndStop(последний кадр)+visible=true`; `opened=true`;
  закрыть reward-событие (иконка HUD жёлтая). Спрайт сундука остаётся на
  карте (НЕ маркер — не удаляется логикой закрытия события; это была
  причина «исчезал»).
- Награда — ТОЛЬКО у доброго: трофеи `rollTrophies(TROPHY_MULT_CHEST)` (см.
  "Система наград (Explore)" ниже; было золото `rand(10,50)` — заменено на
  трофеи, золото в забегах больше не выпадает) через `spawnRewardFloat` (см.
  ниже). Ловушка (мимик, 20%) — чистое наказание, награды нет.
- Explore офлайн: `player.trophies` НЕ начисляется (серверный блок Phase 2.5)
  — здесь только визуальный попап.

⚠️ Грабля: `loadSheetFrames` дефолт `cols=12`. Для листов с иным числом
колонок в ряд ОБЯЗАТЕЛЕН 5-й аргумент (`drink=14`, `Chest_Open=13`,
`Chest_Trap=14`). Иначе последние кадры уходят за пределы картинки → пустая
текстура (сундук «исчезал»).

## Reward float (Explore) — ГОТОВО, переиспользуемый
`spawnRewardFloat(worldX, worldY, rewards[{kind, amount}])` — узлы в МИРОВОМ
контейнере (двигаются с камерой). Формат строки: ЧИСЛО слева, ИКОНКА справа
("+35 <icon>"). Иконка ~24px + Pixi `Text` с тёмной обводкой. Несколько
наград — столбиком.

Анимация: всплывает вверх ~45px за `REWARD_FLOAT_MS=2000`, fade-in в начале /
fade-out в конце, потом `destroy()`. Цвета текста: gold `#E8B23A`, trophy
`#C0653A`, rp `#F08A24`.

Зовётся из сундука (добрый исход), обелиска, смуглера, врага и босса — везде
одним и тем же вызовом (см. "Система наград (Explore)" ниже).

## Система наград (Explore) — ГОТОВО

Единая формула трофеев для всех событий забега (`Explore.tsx`):

```
rollTrophies(multiplier) =
  round(TROPHY_BASE * level^TROPHY_LEVEL_POWER * (0.8 + random*0.4) * multiplier)
```

Константы: `TROPHY_BASE=12.5`, `TROPHY_LEVEL_POWER=0.446`,
`TROPHY_SPREAD=0.4` (разброс ±20% вокруг базового числа — множитель `(1 -
TROPHY_SPREAD/2) + random*TROPHY_SPREAD` = `0.8..1.2`). `level` —
`PLAYER_LEVEL_FALLBACK=1` (ВРЕМЕННО, см. Next Steps: уровень игрока в Explore
пока не пробрасывается, формула всегда считает по 1 уровню).

Множители по типу события — свой `TROPHY_MULT_*` на вызов
`rollTrophies(multiplier)`:

| Событие | Множитель | На 1 уровне | На 500 уровне |
|---|---|---|---|
| Враг (кластер, сумма на группу) | `TROPHY_MULT_ENEMY=1` | 10–15 | 160–240 |
| Обелиск | `TROPHY_MULT_OBELISK=2` | 20–30 | — |
| Сундук (добрый исход) | `TROPHY_MULT_CHEST=3` | 30–45 | — |
| Босс | `TROPHY_MULT_BOSS=4` | 40–60 | — |

Ловушка сундука (мимик, 20% исход) — чистое наказание, награды нет.
Контрабандист — обмен существующих трофеев (×1.5 / кража половины), НЕ
входит в эту систему (не вызывает `rollTrophies`).

**Кластер врагов** — сумма на ВЕСЬ кластер разыгрывается ОДИН РАЗ при
спавне (`rollTrophies(TROPHY_MULT_ENEMY)`), а не при смерти каждого врага
отдельно — иначе `random` на каждую смерть дал бы разные числа и сумма по
группе не сходилась бы с задуманной. Раскладка по врагам: каждому, кроме
последнего, `Math.floor(total / count)`; последний добирает остаток (`total
- floor*(count-1)`) — сумма долей всегда точно равна `total`. Доля хранится
в новом поле `Enemy.trophyReward`, выдаётся через `spawnRewardFloat` в
момент удаления врага из `worldContainer` (после `DEATH_HOLD_MS`); при
`trophyReward === 0` `spawnRewardFloat` не вызывается (не всплывает пустая
надпись).

⚠️ **ЗОЛОТО БОЛЬШЕ НЕ ВЫПАДАЕТ В ЗАБЕГАХ.** Убрано у сундука (было
`rand(10,50)`) и обелиска (были `OBELISK_REWARD_GOLD_MIN/MAX=60/120`,
константы удалены). Золото планируется получать обменом трофеев в меню —
**этот обмен ЕЩЁ НЕ СДЕЛАН** (см. Next Steps). Сейчас игра в переходном
состоянии: золото в забеге взять негде, а магазин (зелья за 20 золота и
т.п.) по-прежнему торгует на золото — до обмена это тупик экономики, не
проверять покупки в отрыве от этого факта.

Рассчитанная, но НЕ применённая формула золота (на будущее, для обмена
трофей→золото или отдельного источника — куда именно, ещё не решено):
```
rollGold(multiplier) =
  round(90 * level^0.30 * (0.7 + random*0.6)) * multiplier
```
Разброс ±30% (шире, чем у трофеев). Не реализована как функция в коде —
просто зафиксированные числа, чтобы не терять подбор.

## Explore / Platforming Engine (Phase 1 — ГОТОВО)

Explore.tsx теперь содержит движок платформинга (игрок ходит/прыгает по карте),
не только показ карты. Игрок пока красный прямоугольник 64×128 (2 тайла).

Физические константы (все вверху Explore.tsx, одно место):
- MOVE_SPEED=4, GRAVITY=0.31, JUMP_VELOCITY=11.5 (было 10, +15% — чтобы
  герой мог перепрыгивать босса; высота подъёма выросла примерно на 32%,
  дальность прыжка тоже увеличилась), MAX_FALL=20
- CAMERA_V_ANCHOR=0.65 (игрок ниже центра экрана)
- WORLD_SCALE=0.75 (зум мира)
Прыжок откалиброван под модель прыжка map_tools: высота ≈2.5 тайла,
вверх-1 и вверх-2 берутся, вверх-3 нет.

⚠️ **Модель проходимости не перепроверена после подъёма JUMP_VELOCITY.**
Модель "dx≤5 вниз / dx≤4 по ровному / dx≤3 вверх-1 / dx≤2 вверх-2 /
вверх-3 запрещён" была построена под `JUMP_VELOCITY=10`. После повышения
до 11.5 модель НЕ перепроверялась. Все шесть карт требуют визуальной
ревизии проходимости: могли открыться запрещённые переходы вверх-3 и
удлиниться горизонтальные прыжки.

Старт: из слот-файла карты (поле start), НЕ эвристикой.
Коллизия читается из .txt сетки, tileSize единый с mapRenderer.

ГЛАВНОЕ: символ '=' переосмыслен. Было — one-way платформа (проходима снизу).
Стало — твердь во всех направлениях, КРОМЕ прохода под полосой:
- блокирует вверх (удар головой), вбок, держит сверху
- блокирует только САМА ПОЛОСА (верхние 44% клетки, PLATFORM_H_RATIO=0.44)
- нижние 56% клетки — свободный воздух, под полосой проходим
- есть защита от застревания игрока под полосой
Это осознанное решение (соулс-лайк, не прыгалка), расходится со старым
описанием '=' в SKILL-maps (документ обновлён отдельно).

Рендер '=': полоса от ВЕРХА клетки (top=y*TS), было — от низа.
PLATFORM_H_RATIO экспортируется из mapRenderer.ts — единый источник для
рендера И коллизии, не дублировать число.

Debug-слои убраны, карта A пройдена ногами от старта до конца (реально проходима).

### Phase 2, часть 1 — HP и шипы (готово)

HP игрока в Explore: maxHp = endurance * 8 (как в старом бою), хранится в ref
(не в state — меняется в игровом цикле каждый кадр), есть HP-бар. При hp<=0 —
конец забега как abandon (потеря трофеев, возврат в меню).

Explore подгружает слот-файл карты: рядом с map_X_*.txt лежит map_X_slots.json,
имя слот-файла выводится из имени карты. Из слот-файла берутся точки событий.

Шипы: точки из поля "hazard" слот-файла вставляются в коллизионную сетку как
символ '^'. Урон 50% maxHp за касание, 1 сек i-frames после касания,
многоразовые (не исчезают), стоять на них нельзя (не твердь для приземления).
Спрайт — public/assets/objects/spikes.png, рисуется в mapRenderer.ts (отдельная
ветка для '^', нижняя часть клетки).

### Phase 2, часть 2 — шипы финализированы, каркас "3 события за забег" (готово, на заглушках)

Шипы финализированы: hazard в map_X_slots.json — пул точек (12 на карте A),
каждый забег случайно ставится 10 из пула (pickRandom, без повторов, без
падения если точек < 10). Урон/i-frames/спрайт — без изменений, работают как
описано выше. Событийные символы в .txt-сетке карт больше НЕ хранятся — сетка
несёт только геометрию ('#','=') и декор ('R','P'); все события (шипы, сундуки,
враги и т.д.) приходят исключительно из map_X_slots.json.

Каркас "3 события за забег" готов на ВРЕМЕННЫХ заглушках: при старте забега
случайно выбираются 3 события из общего слот-пула карты (enemyCluster/сундук/

метки-маркеры вместо настоящих спрайтов. Сверху экрана — 3 иконки HUD (серые
→ жёлтые). Закрытие события пока по касанию хитбоксом (не по бою/атаке —
это заглушка). Когда закрыты все 3 — переиспользован СТАРЫЙ results-экран из
App.tsx (без переделки самого экрана), ему передаются совместимые по формату
данные (rooms/roomIndex/results).

### Phase 2, часть 3 — атака игрока, AI зверя, камера (ФИНАЛ — готово)

**Камера — ФИНАЛ**: зум `WORLD_SCALE=0.55` (закреплено после ручного подбора
временным тюнером — тюнер убран), вертикальный якорь `CAMERA_V_ANCHOR`, плюс
look-ahead — упреждение по направлению движения (`LOOKAHEAD_TILES=1.75`
тайла) с плавной lerp-интерполяцией (`SMOOTH=0.055`, масштабируется по dt —
плавность не зависит от fps). Clamp по краям карты сохранён: target
клэмпится ДО lerp, поэтому камера не показывает за границы карты.

Атака игрока портирована из `Battle.tsx` (числа и правила, не Pixi-код): урон
`15+floor(str/2)`, кулдаун 0.5с (`ATTACK_COOLDOWN`), хитбокс — прямоугольник
по направлению взгляда (`facingRef`), кнопка ⚔. Дальность атаки — уже НЕ
общая `ATTACK_RANGE`, а разделена на `PLAYER_ATTACK_RANGE=56` (меч игрока) и
`ENEMY_ATTACK_RANGE=92` (дальность удара врага, `inMeleeReach`) — см.
"Коллизия тел игрок↔враг" ниже, почему их пришлось развести. "Один удар =
один засчёт" через `attackSwingIdRef`/`lastHitSwingId` у каждого врага.

**AI зверя — ЗАВЕРШЁН** (спрайт подключён — см. "Спрайты и боевая логика
зверя (обычный враг)" ниже; хитбокс-прямоугольник `enemy.rect` остался, но
только как невидимый физический хитбокс под спрайтом):
- **физика** — гравитация (`GRAVITY`/`MAX_FALL`, те же, что у игрока),
  приземление на `'#'`/`'='` тем же `sweepFootBlock`, что и у игрока; в
  ПОГОНЕ падает с края платформы за игроком (разворота у края нет —
  агрессивная физика, осознанное решение), в ПАТРУЛЕ — НЕ падает (см. ниже);
- **агро** — преследует ТОЛЬКО если игрок в пределах `AGGRO_RANGE_TILES=7`
  тайлов по X (было 8, снижено полировкой) И на том же этаже по Y (допуск
  `FLOOR_Y_TOLERANCE=1.5` тайла);
- **патруль** (реализован) — вне агро враг НЕ стоит на месте, а ходит туда-
  сюда вокруг своей точки спавна (`enemy.spawnX`) в пределах
  `±PATROL_RANGE_TILES=3.5` тайла, разворачиваясь на границе зоны/у стены.
  Скорость патруля — ОТДЕЛЬНАЯ фиксированная константа `ENEMY_PATROL_SPEED=
  0.55` (НЕ доля от chase-скорости — так полировку погони можно тюнить не
  трогая патруль). В патруле край платформы — стена: враг разворачивается,
  а не падает (в отличие от погони);
- **погоня** — скорость `ENEMY_CHASE_SPEED=1.12` (было 1, +12% полировкой,
  чуть быстрее патруля);
- **windup-атака** — подходит до `ATTACK_STOP_DIST=45` (~64% исходного
  `ATTACK_RANGE=70`, до разделения дальности — см. `PLAYER_ATTACK_RANGE`/
  `ENEMY_ATTACK_RANGE` в "Коллизия тел игрок↔враг" ниже), ИЛИ до касания тел
  (`bodiesTouchingX`, добавлено позже, см. там же), замах `WINDUP_MS=650`мс
  с видимым телеграфом (danger tint), удар проверяется на strike-кадре
  attack-анимации (см. "Спрайты и боевая логика зверя" ниже) — можно
  уклониться отходом до этого момента;
- **уклонение** — 2 способа: (а) физический отход из зоны поражения к
  моменту удара, (б) кнопка dodge 🔄 — i-frames ~450мс + кулдаун кнопки ~1с
  (числа НЕ из Battle — там dodge просто отменяет замах врага без окна
  неуязвимости, здесь отдельный механизм по прямому заданию задачи).

Enemy-событие = кластер из 3 врагов (враги — независимый список: у каждого
свой HP/AI/таймеры). Закрывается УБИЙСТВОМ всех троих (не касанием) → иконка
HUD жёлтая, как у остальных событий.

⚠️ Прыжок врага за игроком по платформам — ОСОЗНАННО отложен (полноценный
pathfinding — не для MVP). План на будущее — не общий pathfinding, а точечный
"по точкам лестниц" (как поднимается игрок), не сейчас. Пока запрыгнуть выше
врага — рабочий способ оторваться от погони (высота = безопасность).

### Босс (карта C) — ФАЗА 2 (ближний бой) — ЗАВЕРШЕНА
Босс спавнится в точке `slots.boss` (карта C, плоская пара `[30,23]`, не
массив кандидатов, в отличие от `enemyClusters`/`hazard` — читается НАПРЯМУЮ
из слотов, спавн-вызов не меняется). Спавнится **на 100%** — но, в отличие от
зверя/сундука/обелиска (равновероятный кандидат, может не попасть в тройку),
`kind:'boss'` теперь ГАРАНТИРОВАН в `chosenEvents` (см. "ФАЗА 5" ниже) — тем
же приёмом, что Контрабандист на карте D OPEN: кандидат вынимается из пула и
ставится ПЕРВЫМ элементом, остальные `EVENTS_PER_RUN-1` добираются
`pickRandom` из пула без него.

**Итоговые константы** (все тюнеры, которыми они подбирались, из кода убраны):
`BOSS_DRAW_H=240`, `BOSS_OFFSET_Y=-2`, `BOSS_WIDTH=60`, `BOSS_HEIGHT=214`,
`BOSS_MAX_HP=300`, `BOSS_STOP_DISTANCE=149`, `BOSS_MOVE_SPEED=2.0`,
`BOSS_AGGRO_RANGE_TILES=20`, `BOSS_STAGE2_HP_RATIO=0.5`,
`BOSS_MELEE_RANGE=160`, `BOSS_MELEE2_RANGE=200`,
`BOSS_ATTACK_COOLDOWN_MS=600`, `BOSS_HURT_MS=250`, `BOSS_MELEE_DAMAGE=18`,
`BOSS_MELEE2_DAMAGE=26`, `BOSS_STUN_LIMIT=3`, `BOSS_POISE_IMMUNE_MS=1500`.

**Стадии**: stage 1 — атакует ТОЛЬКО Melee; stage 2 (порог `BOSS_STAGE2_
HP_RATIO=0.5`, т.е. HP ≤150 из 300) — Melee или Melee2 случайно 50/50.
Переход в stage 2 считается ОДИН раз, в момент пересечения порога вниз, в
обработчике попадания героя (`applyAttackHit`), не в тикере.

**Poise босса — ДВА слоя, устроен ИНАЧЕ, чем у зверя** (POISE_POINT/
STUN_LIMIT/POISE_IMMUNE_MS зверя боссу не подходят по смыслу — см. грабли
ниже):
- **Слой 1 (главный)** — пока `attackAnimPlaying`, Hurt НЕ проигрывается
  вообще, ни на каком кадре, атака ВСЕГДА доигрывает до strike-кадра;
  вместо хитстана — короткая красная вспышка спрайта (`BOSS_HIT_FLASH_MS`,
  tint), урон при этом проходит нормально.
- **Слой 2** — вне атаки: свои `BOSS_STUN_LIMIT`/`BOSS_POISE_IMMUNE_MS`
  (аналог зверя, но `stunCount` растёт по другому триггеру — см. грабли).
- Итоговые приоритеты состояний: `dead > attack > hurt > walk > idle`
  (attack ВЫШЕ hurt — ключевое отличие от зверя, где hurt может прервать
  замах в ранней фазе).

**Грабли, выстраданные на этой фазе (общий урок, не только про босса):**
- **`hurtTimer` выполняет ТРИ роли одновременно**: гейт старта новой атаки/
  замаха, селектор ветки анимации "играть Hurt" и счётчик оставшегося
  времени хитстана. Отдельного флага "проигрывать Hurt" (по аналогии с
  `attackAnimPlaying`) нет НИ у босса, НИ у зверя — это одна и та же
  числовая переменная на все три роли.
- **Из-за этого длительность Hurt НАПРЯМУЮ определяет, может ли существо
  вообще действовать.** `BOSS_HURT_MS` был ≈1033мс при интервале ударов
  героя ~500мс (`ATTACK_COOLDOWN`) — герой физически попадал чаще, чем
  Hurt успевал закончиться, и `hurtTimer<=0` (гейт старта атаки) никогда
  не открывался: босс не мог атаковать вообще, пока его бьют серией.
  **Правило на будущее**: длительность Hurt должна быть заметно МЕНЬШЕ
  интервала ударов героя, а не подбираться "на глаз по анимации".
- **Попадание не должно продлевать УЖЕ ИДУЩИЙ Hurt** — новый `hurtTimer =
  BOSS_HURT_MS` должен выставляться только если `hurtTimer<=0` на момент
  попадания, иначе серия ударов бесконечно продлевает один и тот же
  хитстан вместо того, чтобы дать ему закончиться.
- **`stunCount` должен расти ТОЛЬКО когда попадание сбивает УЖЕ НАЧАТУЮ
  атаку**, а не от любого попадания. Если считать каждое попадание — счётчик
  на деле меряет темп ударов игрока, а не количество реально сорванных
  действий, и накопительный иммунитет либо не подключается вовремя, либо
  подключается по неверному триггеру.
- **"Hurt прерывает атаку" — ДЛЯ БОССА это ОШИБОЧНОЕ требование.** Если
  хитстан может оборвать атаку в любой момент (как в ранней версии этого
  шага), при серии ударов босс вообще ни разу не доводит атаку до конца —
  бесконечный стан-лок. Решение — слой 1 выше (иммунитет к Hurt во время
  атаки), а не попытка "починить" прерывание тайминг-настройками.

**Смерть** — тело остаётся лежать на месте до конца забега (НЕ despawn'ится,
в отличие от зверя), хитбокс убран (герой проходит сквозь труп, тело не
перегораживает арену), HP-бар над головой скрыт, повторный урон по трупу
не проходит. Награда и закрытие события — см. "ФАЗА 5" ниже.

**`SAME_FLOOR_TOLERANCE_TILES=2.5`** — общая правка: допуск по вертикали в
проверке "на одном этаже" (враг агрится/преследует, только если игрок на
том же этаже), применяется И к боссу, И к обычным врагам. Чинит потерю
агро, когда герой подпрыгивает — раньше прыжок формально уводил игрока
"на этаж выше" и враг замирал.

### Босс (карта C) — ФАЗА 3 (дальний бой) — ЗАВЕРШЕНА

**Итоговые константы**: `BOSS_RANGED_MIN_TILES=6`, `BOSS_RANGED_COOLDOWN_MS=1500`,
`BOSS_RANGED_RELEASE_FRAME=20`, `BOSS_RANGED_DAMAGE=14`, `BOSS_SPIKE_SPEED_X=700`,
`BOSS_SPIKE_GRAVITY=1400`, `BOSS_RANGED_DOUBLE_CHANCE=0.5`, `BOSS_SPIKE_HAND_X=0.061`,
`BOSS_SPIKE_HAND_Y=0.376` (координаты кисти на листе Boss_Ranged, доля ширины/
высоты клетки, замерены по кадру выпуска).

**Решение изменено против исходного ТЗ** ("бросок от бедра, низко, траектория
прямая горизонтальная") — реальная анимация Boss_Ranged даёт ВЫСОКИЙ бросок:
кисть на кадре выпуска находится ~200px над землёй и по ходу ролика только
поднимается, низкого кадра с вытянутой рукой на листе нет. Прямой горизонтальный
шип пролетал НАД головой героя. Заменено на баллистическую дугу
(`BOSS_SPIKE_GRAVITY`) с прицеливанием: начальная `vy` подбирается при спавне так,
чтобы дуга прошла через центр героя НА МОМЕНТ броска (не самонаводка — дальше
герой может уйти), шип разворачивается по вектору скорости (`atan2(-vy,-vx)`)
вместо зеркалирования через `scale.x`.

**1-2 шипа за бросок** — количество разыгрывается ОДИН раз на старте броска
(`rangedShotsLeft`, `BOSS_RANGED_DOUBLE_CHANCE` — шанс второго). Второй шип —
повтор ТОЙ ЖЕ анимации ranged с нулевого кадра БЕЗ возврата в стойку (прямой
`gotoAndPlay(0)`, т.к. `playBossAnim` не рестартит уже активный `kind`), кулдаун
стартует только после последнего шипа. Прицеливание второго шипа считается
заново по текущей позиции героя (та же формула `vy`, что и на первом).

**Приоритет** — ranged встроен как полноценное состояние (`rangedAnimPlaying`/
`rangedThrowApplied`/`rangedShotsLeft`), тот же слой 1 иммунитета к Hurt, что у
melee (см. ФАЗА 2 выше): `dead > attack > ranged > hurt > walk > idle`. Доступен
с ПЕРВОЙ стадии (в отличие от Melee2). Триггер — герой в агро и дальше
`BOSS_RANGED_MIN_TILES`, кулдаун истёк — иначе идёт в ближний бой.

**Грабли, выстраданные на этой фазе:**
- **Точка вылета снаряда — от трансформа СПРАЙТА, не физического бокса.**
  `boss.x`/`boss.y`/`BOSS_HEIGHT` — координаты хитбокса, рука нарисована в
  клетке спрайта — системы координат разные и разъедутся при нормализации
  листа (см. Boss_Ranged в таблице выше). Спавн считается через `sprite.x/y`,
  `anchor`, `scale` и `BOSS_SPIKE_HAND_X`/`BOSS_SPIKE_HAND_Y`.
- **Boss_Spike_Impact.png — cols=10, не 12** (дефолт `loadSheetFrames`).
  Пятый аргумент обязателен, иначе кадры уезжают за пределы листа.
- Попадание в пол по ходу дуги проверяется ТЕМИ ЖЕ `isSolid`/
  `isPlatformBandBlocking`, что и остальная физика карты — отдельной проверки
  для снарядов не писали.

✅ Boss_Ranged.png нормализован подбором и зафиксирован числом —
`BOSS_SCALE_FIX_RANGED=1.00`, `BOSS_ANCHOR_X_RANGED=0.593`,
`BOSS_ANCHOR_Y_RANGED=0.985` (см. таблицу и примечание выше). Лист
по-прежнему НЕ пересобран в общий пиксельный масштаб персонажа (это отдельный
вопрос, не блокирует игру) — нормализация здесь через подбор поверх исходных
размеров листа, не через пересборку кадров.

### Босс (карта C) — ФАЗА 5 (награда/закрытие) — ЗАВЕРШЕНА

Босс теперь ВХОДИТ в рулетку 3 событий, а не спавнится мимо неё: `kind:'boss'`
кандидат ГАРАНТИРОВАН в `chosenEvents` (та же схема, что у Контрабандиста на
карте D OPEN, см. "Особая механика: тайник карты D" ниже) — вынимается из
пула `buildEventCandidates` и ставится ПЕРВЫМ элементом, остальные
`EVENTS_PER_RUN-1` добираются `pickRandom` без него. Индекс запоминается в
`bossEventIndexRef` (по образцу `obeliskEventIndexRef`) внутри
`chosenEvents.map`, тем же способом, что у обелиска. Сам спавн босса
(`spawnBoss`, чтение `slots.boss`) НЕ изменился — точка совпадает с точкой
гарантированного кандидата.

**Момент выдачи** — конец death-анимации, определяется ТЕМ ЖЕ способом, что
у зверя: `boss.sprite.currentFrame >= bossFramesByKind.death.length - 1 ||
!boss.sprite.playing`. Проверяется в НОВОЙ `else`-ветке того же `if
(!boss.dead)` блока в тикере (труп при этом по-прежнему НЕ despawn'ится —
только награда/закрытие, без удаления). Новое поле `Boss.rewardGiven`
дедупит выдачу — без флага туша, висящая на последнем кадре анимации сколько
угодно, слала бы награду каждый тик.

**Награда** — трофеи по общей формуле (см. "Система наград (Explore)" ниже):
`rollTrophies(TROPHY_MULT_BOSS)`, `spawnRewardFloat` над телом (тот же вызов,
что у обелиска: `sprite.x`, `sprite.y - sprite.height`), затем
`closeEvent(bossEventIndexRef.current)`.

### Управление с клавиатуры (НОВОЕ)

В Explore.tsx добавлено управление с клавиатуры как ВТОРОЙ способ ввода, рядом
с экранными кнопками (не вместо них) — оба способа дёргают одни и те же refs.

Сравнение идёт по `e.code` (физическая клавиша), НЕ по `e.key` (символ,
зависящий от раскладки) — на `e.key` был реальный баг: на русской раскладке
буквенные клавиши (`j`/`k`/...) не срабатывали вообще, т.к. `e.key` отдавал
русскую букву, а не латинскую. `e.code` раскладконезависим.

Маппинг: движение `ArrowLeft`/`KeyA` и `ArrowRight`/`KeyD` (удержание, keydown
старт / keyup стоп); прыжок `ArrowUp`/`Space`; атака `KeyJ`; dodge `KeyK`;
зелье `KeyH`; скиллы `Digit1`/`Digit2`. Разовые действия (прыжок/атака/dodge)
— с `e.repeat`-guard, чтобы удержание клавиши не спамило действие каждый
кадр. `preventDefault()` на `ArrowUp`/`ArrowLeft`/`ArrowRight`/`Space`, чтобы
страница не скроллилась. Слушатели `keydown`/`keyup` вешаются на `window`
один раз в `useEffect` и снимаются в cleanup (важно под React 19 StrictMode —
без снятия слушатель дублируется при двойном монтировании в dev).

### Спрайты героя (idle/run/jump/attack/hurt/death) — ГОТОВО

Спрайты героя пережаты до высоты клетки 296px (ужимали с исходных 512px под
потолок `resolution:2`, экранная высота героя ~140px, т.е. ~280 физических px
— исходник близок к размеру отрисовки, передискретизация минимальна). Единая
клетка на ВСЕ анимации героя — 394×296 (см. "Готовые ассеты — Герой" выше).
Все файлы — `public/assets/sprites/hero/{idle,run,jump,attack,hurt,death,
drink}.png`.

- **Прыжок**: не проигрывается покадрово — статичная ПОЗА по знаку `phys.vy`
  (взлёт = кадр 10, падение = кадр 15 в jump.png), ноги приклеены к боксу
  через `anchor.y` (не 1.0, как обычно, — там ноги внутри клетки подняты).
  Плюс короткое **land** (приземление, кадры 18-24 того же jump.png) при
  касании земли — доигрывает один раз, прерывается движением или новым
  прыжком.
- **Атака**: урон наносится на КАДРЕ УДАРА (`ATTACK_STRIKE_FRAME=6` из 14),
  НЕ в момент нажатия кнопки — раньше было мгновенно по нажатию. `facing`
  фиксируется на старте замаха (`attackFacingRef`) и не меняется до конца
  анимации, даже если игрок зажал движение в другую сторону.
- **Hurt**: хардкор-хитстан — перебивает и обрывает собственный замах атаки
  игрока (не только заглушает контроль); на время hurt новая атака
  заблокирована.
- **Death**: при hp≤0 не мгновенный abandon — сначала проигрывается death
  один раз, последний кадр держится ~0.5с, и только потом срабатывает тот же
  `onClose`/abandon (потеря трофеев), что раньше вызывался сразу.

### Спрайты и боевая логика зверя (обычный враг) — ГОТОВО

Враг больше НЕ плоский прямоугольник — свой `AnimatedSprite` на каждого врага
кластера (`enemy.sprite`, независимые textures/скорость/флип/фаза), тот же
механизм `loadSheetFrames`/`playSpriteAnim` (аналог `playAnim` героя, первым
аргументом принимает целевой спрайт), что и у героя. Прямоугольник-хитбокс
(`enemy.rect`) остался — physics/AI по-прежнему считается по нему, просто
`visible=false`; спрайт — чисто визуальный слой поверх.

**idle↔walk** — по факту движения по X в этом кадре (враг сдвинулся →
walk, стоит на месте, включая паузу перед атакой → idle). Отдельного `run`
НЕТ — в погоне walk тот же клип, только `animationSpeed` заметно выше, чем
в патруле (`WALK_ANIM_CHASE` vs `WALK_ANIM_PATROL`), чтобы лапы переступали
в темпе более быстрого перемещения. Idle — медленное дыхание, полный цикл
~2.4с (24 кадра).

**Фикс `playSpriteAnim` (скорость walk застревала)**: движок покадровой
анимации зверя обновляет `animationSpeed`, даже когда набор кадров НЕ
меняется (напр. `walk` и в патруле, и в погоне — один и тот же массив
кадров) — раньше ранний `return` (`if (sprite.textures === frames) return`)
выходил ДО присвоения скорости, и она застревала на значении последней
СМЕНЫ кадров (напр. после `hurt`→`walk`), а не текущего состояния
(`aggroed`). Починка: при том же наборе кадров скорость всё равно
обновляется на лету, БЕЗ `gotoAndPlay`/рестарта анимации (кадр продолжается
с текущего места) — рестарт/смена `loop` по-прежнему происходят только при
реальной смене набора кадров.

**Флип** — по `enemy.facing` (тот же источник, что уже двигает врага в AI).
Арт смотрит ВЛЕВО по умолчанию → `facing===-1` (влево) БЕЗ зеркала,
`facing===1` (вправо) — `scale.x` уходит в минус. Не трогается, пока враг
стоит на месте (кроме патруля, где facing всегда = patrolDir) — не дёргается.

**Attack** — запускается на входе в windup, играет ОДИН раз (loop=НЕТ), не
обязана закончиться вместе с windup-таймером (анимация длиннее `WINDUP_MS`
на визуальный follow-through лапы). Урон по игроку — на strike-кадре
анимации (`BEAST_ATTACK_STRIKE_FRAME`), НЕ по истечении таймера — числа урона/
дистанции/дальности при этом не менялись, поменялся только МОМЕНТ проверки.

**Hurt** ("клевок головой") — реакция на попадание, играет один раз
(loop=НЕТ), хитстан = длительность самой анимации (`ENEMY_HURT_MS`, выведена
ИЗ `BEAST_HURT_ANIM_SPEED`, а не задана отдельным числом — не могут разъехаться).

**Poise / анти-стан-лок** — без этого игрок непрерывными ударами мог залочить
зверя навечно (замах всегда отменялся hurt'ом раньше, чем доходил до удара):
- `POISE_POINT=0.25` — доля прогресса текущего замаха (`windupTimer/WINDUP_MS`).
  До этой точки урон ОТМЕНЯЕТ замах (как раньше); после — замах НЕ
  отменяется, зверь доводит удар до strike-кадра как обычно, hurt/хитстан
  не запускаются (только числа/тайминг удара — без изменений).
- Накопительный стан-резист поверх POISE_POINT (гарантия прорыва даже при
  ритмичной долбёжке ровно по фазе замаха): `stunCount` — сколько замахов
  подряд отменено; после `STUN_LIMIT=2` подряд — `POISE_IMMUNE_MS=1200`мс
  иммунитета к прерыванию (перекрывает POISE_POINT независимо от прогресса).
  `stunCount` сбрасывается на любом замахе, дошедшем до strike-кадра.
- Красной вспышки/тинта при позднем/иммунном ударе НЕТ (пробовали — убрано
  по правке) — зверь просто молча дожимает атаку.

**Death** — высший приоритет анимаций (`death > hurt > attack > walk/idle`),
перебивает всё немедленно и больше НЕ прерывается (хиты после смерти —
no-op, `enemy.dead` гейт в начале и hit-теста, и основного цикла). Играет
один раз, последний кадр держится `DEATH_HOLD_MS=500` (общая с героем
константа), затем враг удаляется и декрементирует `remainingEnemies` своего
события — закрытие события (иконка HUD) теперь срабатывает ПОСЛЕ hold
последнего убитого врага, не мгновенно на добивающем ударе. Падение НЕ
центрируется/не флипается по ходу — зашито в кадры, facing/позиция
замораживаются на моменте смерти (мёртвый враг пропускает всю физику/AI —
не двигается, не бьёт, не сталкивается с игроком).

**Привязка к полу** — Y отрисовки спрайта берётся с поверхности тайла
(`findGroundSurfaceY`, та же логика, что держит от падения сквозь пол), а не
с низа грубого прямоугольника-хитбокса, + ручная подстройка `FOOT_TUNE=11`px
(общая константа для героя И врагов, подобрана вживую отладочным тюнером).

Все состояния/таймеры (`hurtTimer`, `windingUp`/`windupTimer`,
`attackAnimPlaying`, `stunCount`, `poiseImmuneTimer`, `dead`,
`deathHoldTimer`) — поля на объекте `Enemy`, каждый враг кластера независим.

### Коллизия тел игрок↔враг + боевые фиксы вплотную (ГОТОВО)

**Живой враг — мягкая стена по ГОРИЗОНТАЛИ**: игрок не проходит сквозь врага
сбоку, выталкивается по X к ближайшему краю (`phys.x = enemy.x - PLAYER_WIDTH`
или `enemy.x + ENEMY_WIDTH`, зажато `clamp`). Только по X — вертикаль не
трогается (на врага нельзя встать сверху, можно перепрыгнуть). Мёртвые
(`enemy.dead`) — проходимы (упор физически недостижим, `continue` в начале
итерации цикла врагов). Враги между собой НЕ толкаются — коллизия только
игрок↔враг.

**Перепрыгивание отключает упор**: гейт `verticalReach` + `PUSH_TOP_MARGIN=
0.35` (доля высоты врага сверху, которая НЕ считается "телом" для упора) —
если ноги игрока выше этой линии, считается перелёт, упор не применяется.

**Атака врага вплотную (`bodiesTouchingX`)**: раньше старт windup требовал
`dist <= ATTACK_STOP_DIST` (45), но боковой упор физически не пускает центры
ближе `(PLAYER_WIDTH+ENEMY_WIDTH)/2 = 80` — враг мог упереться в игрока и
бесконечно толкаться, ни разу не начав замах ("толкается, но не бьёт").
Добавлен `bodiesTouchingX` — горизонтальное касание хитбоксов с допуском
`TOUCH_EPS=4`px (граничный случай "ровно впритык" после выталкивания не
ловился строгими `>`/`<`, нужны были `>=`/`<=` с допуском). И старт windup,
И нанесение урона на strike-кадре теперь проверяются по `(inMeleeReach ||
bodiesTouchingX)` — та же рассинхронизация порогов чинилась в двух местах
отдельно (сначала для windup, потом отдельно обнаружилась и для урона на
strike-кадре — они читают порог независимо друг от друга).

**Замах не прерывается дистанцией**: начатый `windingUp` доводится до
strike-кадра ВСЕГДА, даже если игрок отошёл в процессе — попадание/промах
решается только на strike-кадре по факту текущей дистанции/facing, не по
дистанции на старте замаха. Во время замаха враг стоит на месте (движение
живёт только в ветке `!enemy.windingUp`).

**В паузах между ударами враг не толкается**: в ветке погони добавлено
условие `!bodiesTouchingX` — если тела уже касаются, враг НЕ продолжает
лезть вперёд (`enemy.x` не двигается), просто стоит вплотную и ждёт
`attackTimer`. Если контакт разорван (игрок отошёл, замах не начат) — погоня
возобновляется автоматически.

**Урон врага только СПЕРЕДИ (`playerInFront`)**: удар на strike-кадре
проходит, только если игрок с той стороны, куда враг СМОТРИТ (`enemy.facing`,
`1`=вправо/`-1`=влево, тот же источник, что и флип спрайта) — забежал за
спину во время замаха = промах, это способ уклонения. Между замахами
(`!windingUp`) враг доворачивается лицом к игроку по знаку `dx`, ДАЖЕ стоя
вплотную и не двигаясь (`enemy.x` не трогается, меняется только `facing`) —
иначе следующий замах после "забежал за спину" снова шёл бы в пустоту, т.к.
враг так и не развернулся. Во время самого замаха `facing` зафиксирован.

### Прыжковый боевой хитбокс игрока (ГОТОВО)

В прыжке (`!phys.onGround`) уязвимая зона игрока — ОТДЕЛЬНЫЙ уменьшенный
хитбокс по корпусу (поза наклонена, ноги поджаты, меч/плащ торчат наружу —
обычный хитбокс на весь рост в прыжке был бы неточным), через функцию
`getPlayerCombatBox()`: на земле возвращает обычный `PLAYER_WIDTH×
PLAYER_HEIGHT`, в воздухе — `JUMP_HIT_WIDTH=54 × JUMP_HIT_HEIGHT=100`,
центрированный по X относительно `phys.x` и смещённый вниз на
`JUMP_HIT_OFFSET_Y=40` от `phys.y` (числа подобраны вживую отладочным
тюнером с ползунками — тюнер убран из кода, финальные числа захардкожены).

Применяется ТОЛЬКО в боевых местах — `dist`/`verticalReach`/`bodiesTouchingX`/
push-out игрок↔враг/`playerInFront` на strike-кадре врага. Физика
(приземление `sweepFootBlock`, стены по X, потолок `sweepHeadBlock`, шипы) и
хитбокс атаки ИГРОКА остаются на обычном `PLAYER_WIDTH×PLAYER_HEIGHT` — не
трогались. В прыжке игрок физически не может атаковать (анимация прыжка
перебивает attack-ветку в приоритете тикера раньше, чем та успевает нанести
урон), так что отдельного боевого хитбокса для атаки игрока в прыжке не
требуется.

**Финальные размеры хитбоксов** (подобраны вживую отладочными тюнерами,
тюнеры убраны из кода): `PLAYER_WIDTH=54` (было 64), `PLAYER_HEIGHT=128`;
`ENEMY_WIDTH=116` (было 96), `ENEMY_HEIGHT=80` (было 64); дальность атаки
разделена на `PLAYER_ATTACK_RANGE=56` (меч игрока) и `ENEMY_ATTACK_RANGE=92`
(удар врага, `inMeleeReach`) — раньше была одна общая `ATTACK_RANGE=70`.

### Прыжковый физический хитбокс — удар головой (ГОТОВО)

Отдельно от боевого бокса выше: в прыжке (`phys.vy < 0`, взлёт) ВЕРХ
физического хитбокса, которым игрок бьётся головой о потолок/платформу '=',
тоже опущен на `JUMP_HIT_OFFSET_Y=40` (`headOffset = phys.onGround ? 0 :
JUMP_HIT_OFFSET_Y`) — иначе полный `PLAYER_HEIGHT` (128) торчит головой выше
макушки прыжковой позы спрайта, и игрок упирается в пустоту над телом.

Смещение применяется СОГЛАСОВАННО в ОБОИХ местах, где считается удар головой:
- `sweepHeadBlock` — верх пути проверки сдвинут на `headOffset`, снап при
  попадании `phys.y = pushTo - headOffset`.
- "stuck-under-band rollback" (`isOverlappingAtFrameStart`, случай "зашли
  сбоку под ступень") — верх диапазона тоже сдвинут на `headOffset`, но НИЗ
  диапазона намеренно ОСТАВЛЕН на `startY + PLAYER_HEIGHT` (не сдвинут).
  Если ужать оба края на `headOffset`, нижняя граница проверки уезжает в
  клетку под ногами игрока и rollback ложно срабатывает КАЖДЫЙ кадр прыжка —
  прыжок происходит на месте (игрок не взлетает). Это реально ловили и
  чинили — если трогать этот блок снова, держать низ диапазона неподвижным.

НИЗ хитбокса (ноги) и приземление (`sweepFootBlock`, `phys.vy > 0`) НЕ
тронуты — считаются по обычному `PLAYER_HEIGHT`, как и раньше. На земле
`headOffset=0`, поведение не меняется.

**Боковая коллизия в прыжке (ФИКС сессии):** горизонтальная проверка стены
(движение по X, упор в '#' и полосу '=') раньше брала ВЕРХНЮЮ точку от полного
PLAYER_HEIGHT даже в прыжке — из-за этого при диагональном прыжке под нависающей
твердью ("двери"/перемычки) игрока ложно стопорило. Пофикшено: верхняя точка
боковой проверки тоже опущена на headOffset (phys.y+headOffset+1) в ОБЕИХ ветках
(vx>0/vx<0), средняя и нижняя точки не тронуты. Диапазон проверки полосы
(isPlatformBandBlocking) — верхняя граница сдвинута на headOffset, нижняя
оставлена на phys.y+PLAYER_HEIGHT (как в stuck-under-band rollback — оба края
сдвигать нельзя).

### Особая механика: тайник карты D (OPEN/SEALED, 50/50) — ГОТОВО
При заходе на карту D — бросок 50/50: OPEN или SEALED (сейчас катится в тестовой
кнопке "D Тайник (50/50)" в App.tsx; при общем рандоме карт переедет в единый
загрузчик). OPEN → тайник доступен, спуск на дно ямы открыт, И Контрабандист
ГАРАНТИРОВАН одним из событий забега. SEALED → тайник завален, Контрабандиста
нет.
Файлы переименованы к простому шаблону: `map_D_OPEN.txt` / `map_D_OPEN_slots.json`
/ `map_D_SEALED.txt` / `map_D_SEALED_slots.json` (старые map_D_tainik*.txt и
map_D_slots.json удалены). `slotsFileForMap` в Explore.tsx получила спец-ветку
для карт с суффиксом состояния (map_D_* → слоты = имя.txt с заменой .txt на
_slots.json; остальные карты A/B/C/E/F — по первому токену, как раньше).
⚠️ Старый дизайн (был тут раньше: "пустой ролл Смуглера заваливает тайник")
БОЛЬШЕ НЕ АКТУАЛЕН — причина/следствие перевёрнуты.

**Гарантия OPEN→Контрабандист — РЕАЛИЗОВАНА** в `setup()` (Explore.tsx),
прямо перед формированием тройки событий: при `mapFile.startsWith('map_D_OPEN')`
кандидат-смуглер вынимается из общего пула (`buildEventCandidates(slots)`) и
ставится ПЕРВЫМ элементом `chosenEvents`, оставшиеся два добираются обычным
`pickRandom` из пула БЕЗ него (не задваивается). Порядок тройки НАМЕРЕННО не
перемешивается — иначе смуглер не был бы гарантирован *в конкретной позиции*,
хотя гарантия попадания в тройку сохранилась бы.
На SEALED ничего дополнительно исключать не нужно: в `map_D_SEALED_slots.json`
`npc.smuggler = null`, а `buildEventCandidates` молча пропускает типы без точек
— смуглер туда и так не попадает в пул.
⚠️ Известное следствие: иконка Контрабандиста в HUD-плите всегда ПЕРВОЙ (левое
гнездо из трёх) при OPEN — то есть состояние карты D читается по HUD ещё до
спуска в яму (спойлер по факту гарантии + фиксированного порядка). Если это
станет проблемой — чинить перемешиванием итоговой тройки (`chosenEvents`)
ПОСЛЕ вставки смуглера, а не отказом от гарантии.
⚠️ Механизм узкий и специфичный для карты D: проверка `mapFile.startsWith(...)`

### Особая механика: Обелиски (карта F, заменяет Загадку) — ГОТОВО
10 точек-кандидатов на всех 4 ярусах карты, `slots.obelisk?.points`. Обелиск —
рядовое событие рулетки 3 событий (см. "Готовые ассеты — Загадка-обелиск" выше
для полной механики/констант/арта): не выпал в тройку — на карте его нет.
Выпал → 1 обелиск в `idle` в случайной точке → удар → `burning` + старт события
+ таймер 30 сек + доспавн ещё 3 (рандом из оставшихся точек) → каждый следующий
удар +15 сек (таймер НЕ фиксированный) → все 4 сбиты = золото 60–120 +
`closeEvent`, обелиски гаснут в `idle` декорацией; таймер истёк = смерть героя
через обычный путь death, событие не закрывается.
✅ Вопрос "максимальная дистанция между обелисками может не влезть в 30 сек"
ЗАКРЫТ добавкой времени за удар (таймер растёт, не фиксирован).

### Параллакс в Explore (2 живых слоя, НЕ часть канваса карты)

снимается в cleanup перед `app.destroy()`.

### Грабли текстур карты (выстраданы, не наступать)
- **`texSrc()`: атлас 8 КОЛОНОК × 4 СТРОКИ, не 8×8.** Брали остаток от 8
  и по Y тоже — для `y % 8 >= 4` координата уходила НИЖЕ нижний край
  картинки, и `drawImage` молча рисовал пустоту БЕЗ единой ошибки в
  консоли. На карте A все три этажа (y=6,13,20 — остатки 6,5,4) попали
  в этот диапазон, поэтому кладки не было нигде.
- **Светлая «истёршая» кромка есть только в ВЕРХНЕЙ строке атласа**
  (у `masonry_graveyard` нижние строки ровные — замерено по яркости).
  Поэтому файлы-поверхности всегда берут строку 0, а файлы под землёй —
  строки 1..3. Разнообразие даёт горизонталь (8 колонок). Иначе полы
  разных этажей выглядят по-разному.
- **Не файлить одну и ту же ячейку и на поверхности, и под землю** —
  светлая кромка повторяется на каждом ряду и читается как «лестница».
- **Старый атлас имел тёмные полосы ~5-6px между ячейками**, они
  «протекали» в игру как трещины между камнями — лечилось обрезкой
  `INSET`. В НОВЫХ атласах полос нет (проверено замером яркости на
  границах), `INSET` снижен до 2px.
- **`Assets.load()` реджектит промис при 404**, в отличие от
  `loadSprites()` в `mapRenderer.ts` (та всегда резолвится). Один
  недостающий PNG фона в async `setup()` обрывал ВСЮ инициализацию — с
  ним пропадала и твердь, и геймплей. Загрузку фона обязательно
  оборачивать в try/catch: нет фона — играем без фона, а не белый экран.
- **Полноаливое проглатывание ошибки загрузки** (`img.onerror` без лога)
  стоило нескольких итераций вслепую — в `loadSprites()` теперь
  `console.error` с путём.

### Расстановка декора по картам (`tools/place_decor.py`)
Декор в `map_X_slots.json` лежит массивом `decor: [{x, y, type}]`. Раскладка
делается офлайн-скриптом, НЕ вручную и НЕ рандомом в рантайме — иначе объекты
висят в воздухе и врастают в потолок.

Правила (согласованы с Андреем, менялись по ходу — здесь итоговые):
- **Опора обязательна**: напольный декор ставится в клетку, под которой `#`
  или `=`. Подвесной (`crypt_hanging_chains`) — только под клеткой `#`,
  НЕ под `=`: цепь с тонкой однoклеточной платформы читается как ошибка,
  не за что цепляться. Под цепью ≥3 клетки воздуха, разнос между цепями
  ≥5 тайлов.
- **Высота проверяется**: `headroom` считает воздух над клеткой, объект выше
  запаса не ставится (густое дерево 4 тайла не влезет под низкий потолок).
- **На платформах `=` — только мелочь** (≤1.6 тайла: кости, груда золота,
  раскопанная могила). Крупное — только на сплошной `#`.
- **Зона чистоты ТОЛЬКО вокруг гейм-точек** (1 тайл). Изначально закладывал
  чистоту вокруг всего геймплея — Андрей отверг: декор не имеет коллизии и
  служит восприятию карты, вылизанные пустоты вокруг каждого объекта делают
  карту беднее. К врагам/наградам декор подходит вплотную, поверх их клетки
  не встают. Вокруг НПС/босса/старта — 1-2 тайла (окно диалога, обзор).
- **Отступ от краёв карты** (x=0 и x=W-1 пропускаются) — иначе объект
  срезается краем экрана.
- **Группами по 1-3** с интервалом ~4 сверху / ~2 внизу: ниже по карте
  гуще (нижние этажи обжитее). Тип выбирается ВЗВЕШЕННО, не жёстким
  отбором: крупное тяготеет к стенам, мелкое к открытым местам, повтор
  подряд глушится ×0.25. Жёсткий топ-3 по размеру пробовал — половина
  набора (фонари, статуи) не выпадала вообще.

Плотность на выходе: карта A — 48 объектов, карта B — 34 (на B меньше:
верхнее плато почти целиком занято врагами/наградами/шипами).

Валидатор проверяет: опору, высоту, потолок для цепей, дубли, попадание на
геймплейную клетку, край карты. Обе карты — 0 ошибок.

**Превью до применения:** офлайн-рендер на Python (PIL) повторяет логику
`mapRenderer.ts` (тот же атлас 8×4, тот же выбор строки, тот же 0.42 dim) и
даёт PNG всей карты + кроп в масштабе 1:1. Смотреть надо кроп: общий план
3072px мельчит и ничего не видно, а игрок видит ~1100px участок.

**Статус:** A и B разложены и приняты. C, D, E, F — не сделаны.

## Магазин (КАРКАС ГОТОВ, сервер не подключён)

### РОЛИ ВАЛЮТ
- Золото — покупается ВСЁ. Приумножить нельзя.
- Трофеи — только обмен на золото. Ценны тем, что контрабандист
  в забеге умножает их x1.5 (риск). Поэтому трофей дороже золота
  по смыслу, и обмен — это решение "хватит рисковать".
- RP — под уникальные предметы (супер-амулет и т.п.), механика
  не проработана, валюта пока просто копится.

Расходники / Улучшения / Снаряжение / Книги скиллов. Обмен

работа с кошельком, а не товар).

### ВЁРСТКА
Выбрана после нескольких итераций — Андрей отверг варианты со
списком строк ("похоже на обычное приложение"):
- ВИТРИНА СЕТКОЙ 3 колонки: предмет = картинка + цена под ней.
  Названий и описаний на витрине НЕТ.
- Вкладки разделов — горизонтальный ряд под шапкой.
- Недоступное (не хватает золота / не открыто по уровню) —

  (слово, не процент) либо "Броня 4 → 6" для улучшений
- счётчик количества (− N +) ТОЛЬКО у расходников;
  у улучшений счётчика нет
- кнопка покупки показывает ИТОГОВУЮ сумму за выбранное

  предмет есть. Нарочно тихая (серая, мельче кнопки покупки),

## Система предметов (СПРОЕКТИРОВАНА, не реализована)

### ИСТОЧНИКИ
Предметы падают ТОЛЬКО в забеге — из сундуков, врагов, босса,
обелисков. В магазине можно докупить и продать, но магазин не
основной источник.

### ПРАВИЛО
Одно название = один фиксированный набор характеристик. Редкости
НЕТ, разброса статов НЕТ. "Железный шлем" всегда одинаковый.
Прогрессия идёт разными предметами, а не разбросом.

### ТИРЫ
6 штук, открываются по уровню героя — 1, 5, 10, 15, 20, 25.
Источник влияет только на ШАНС выпадения, не на тир.

### ЛЕСТНИЦА НАЗВАНИЙ
Одинаковая во всех слотах, тир читается по слову: ржавый/драный →
солдатский → дознавателя → гвардейский → безымянного → правого
места. Так комплект одного тира опознаётся на глаз.

### "СКОРОСТЬ ПРОКАЧКИ"
Множитель к существующей системе роста статов (см. раздел "Stat &
Leveling System"). Статы растут от действий: выносливость от
полученного урона, сила от нанесённого, ловкость от использования
скиллов. Предмет ускоряет накопление в процентах.

### ТАБЛИЦА (тир: 1/2/3/4/5/6)
- Оружие: урон 5/10/15/20/25/30 + рост СИЛЫ 5/10/15/20/25/30%
- Шлем: броня 2/5/8/10/13/15
- Броня: броня 5/10/15/20/25/30 + рост ВЫНОСЛИВОСТИ
  5/10/15/20/25/30%
- Перчатки: броня 2/5/8/10/13/15 + рост ЛОВКОСТИ
  5/10/15/20/25/30%
- Сапоги: скорость передвижения 2/4/6/8/9/10%
  (ПОТОЛОК 10% — намеренно, чтобы не сломать платформинг на уже
  размеченных картах)
- Амулет: удача 1/2/3/4/5/7

Броня в сумме (шлем+броня+перчатки): 9 на Т1, 60 на Т6.

### ИНВЕНТАРЬ (СПРОЕКТИРОВАН, фронт-каркас готов)
- Вкладка "Снаряжение" = ИНВЕНТАРЬ. Надетое здесь НЕ дублируется,
  оно на экране "Персонаж".
- 30 ячеек стартово. Расширяется в магазине за золото: +1 ячейка
  за уровень, цена растёт, ПОТОЛКА НЕТ (как закалка). Конкретные
  цены не определены.
- ПУСТЫЕ ЯЧЕЙКИ НЕ РИСУЮТСЯ. Свободное место видно по счётчику
  "N / 30" в шапке. Пустой инвентарь — текст "Пусто".
- Одинаковые предметы СТАКАЮТСЯ: одна ячейка + плашка "×N".
  Одна ячейка = один ВИД зелья независимо от количества.
- В инвентаре лежит ВСЁ, что является предметом: снаряжение,
  зелья, в будущем обереги, карты, книги скиллов.
  Позже появятся предметы, НЕ занимающие места — пока не
  определены.
- ПЕРЕПОЛНЕНИЕ: новый предмет НЕ подбирается, в забеге
  показывается сообщение.
- СОРТИРОВКА ФИКСИРОВАННАЯ, новый предмет встаёт на своё место,
  а не в конец. Порядок групп: weapon, helmet, armor, gloves,
  boots, amulet, potion. Внутри группы — по тиру/силе
  ПО УБЫВАНИЮ (лучшее сверху). Пересчитывается при любом
  изменении списка.
- Сетка 5 колонок, ячейка квадратная, иконка на всю ячейку.
- Тап по ячейке — карточка предмета (тот же оверлей, что
  в магазине): иконка, название, описание курсивом,
  характеристики, кнопки "Надеть" и "Продать".
  У зелий кнопки "Надеть" НЕТ, только "Продать".

  с некоторой вероятностью.
- ТИР ВЫПАВШЕГО ПРЕДМЕТА НЕ МОЖЕТ ПРЕВЫШАТЬ ТИР, ОТКРЫТЫЙ
  ПО УРОВНЮ ГЕРОЯ. Уровень 10 → открыты тиры 1-3 → падает
  максимум тир 3. Это же правило действует и для зелий.
- Найденное копится в забеге и разбирается на экране итогов.
  ПРИ СМЕРТИ ТЕРЯЕТСЯ вместе с трофеями.

### МЕХАНИКА ЗЕЛИЙ В ЗАБЕГЕ
- В забег берётся 3 заряда (как сейчас в коде).
- Заряды набираются АВТОМАТИЧЕСКИ из склада, игрок не выбирает.
  Берутся ЛУЧШИЕ доступные: есть по одному каждого вида —
  сначала уйдёт самое сильное, потом следующее по силе.
- Если зелий на складе нет — забег начинается БЕЗ зелий.
  Меньше трёх на складе — берётся сколько есть.
- ИКОНКА КНОПКИ ЗЕЛЬЯ В ЗАБЕГЕ показывает то зелье, которое
  выпьется СЛЕДУЮЩИМ. Кончилось сильное — иконка сама
  меняется на следующее по силе. Иконка динамическая,
  не статичная.
- ВЫПИТОЕ СПИСЫВАЕТСЯ СО СКЛАДА НАСОВСЕМ, даже если герой
  погиб сразу после. Иначе смерть станет способом сэкономить
  зелья.

## Design Decisions
- Leveling OR not AND (Method 1: +3 End OR +6 Str+Agi combined)
- Puzzle = game-mechanics quiz
- Stat normalization by level factor
- Heal/potions don't affect Endurance growth (totalDamageTaken tracked separately)
- actualHpLost sent to server for correct HP carry between rooms
- Enemy base stats: normal 120HP/14dmg, boss 200HP/18dmg
- Wide arena (3000px) with camera follow
- Флип по направлению в Explore ГОТОВ и разный для героя/зверя (проверено на
  реальных ассетах, не общее правило "sprites face left by default"): герой
  смотрит ВПРАВО по умолчанию (facing===1 → без зеркала, facing===-1 →
  scale.x в минус), зверь смотрит ВЛЕВО по умолчанию (facing===-1 → без
  зеркала, facing===1 → scale.x в минус) — см. "Спрайты героя"/"Спрайты и
  боевая логика зверя" выше. В Battle.tsx (старая боевая сцена) этот флип
  ещё не переносился — там актуальность прежнего допущения не проверялась.
- **Обрыв связи в забеге — вариант А, ПРИНЯТО.** Свернул приложение — игра
  замирает в памяти и продолжается сама при возврате, ничего специально
  делать не надо (проверено вживую). Закрыл приложение полностью — забег
  закрывается как смерть: при следующем входе показывается экран итогов,
  трофеи сгорают. Никакого промежуточного сохранения состояния забега НЕ
  делаем. Причина отказа: любое сохранение, которое откатывает игрока
  назад при переоткрытии, делает закрытие приложения выгоднее смерти
  (закрыл перед боссом на низком HP — получил бесплатный ретрай). Правило
  на будущее: закрыть приложение никогда не должно быть выгоднее, чем
  умереть в забеге. Плюс варианта А — сам момент закрытия ловить не нужно
  вообще: сервер видит открытый `currentRun` при следующем входе и
  закрывает его сам.
