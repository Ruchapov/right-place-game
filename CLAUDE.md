## Mentor Rules
- Beginner solo dev. ONE step at a time. Explain WHAT/WHY, then HOW to verify.
- Commands for **cmd** (not PowerShell). Russian is fine.
- When broken: ask for actual error before guessing.
- Design decisions in chat; Claude Code applies edits in terminal.

## Critical Gotchas
- **Server dev runner is `tsx`** — `ts-node --esm` had Windows ERR_MODULE_NOT_FOUND bug.
- **Server imports need .js extension**: `from '../auth.js'` not `from '../auth'` (ESM)
- **Two auth.ts files**: `server/src/auth.ts` (Telegram verify) vs `server/src/routes/auth.ts` (login route)
- **Run server from server/**: prompt must read `...\telegram-game\server>`
- **After `npm run deploy`**: `•••` → Reload Page in Telegram (aggressive caching)
- **Render auto-deploy sometimes doesn't fire** → Manual Deploy → Deploy latest commit
- **Prisma `migrate dev` reset prompt**: NEVER auto-confirm — already wiped test data once.
- **Open as Mini App** (t.me/RightPlaceGame_bot/game) — initData only works in Telegram, NOT in browser
- **UI-отладка теперь и через `localhost:5173/right-place-game`** (`npm run
  dev -- --host`, hot-reload): `App.tsx` при отсутствии/ошибке
  `retrieveRawInitData()` (т.е. вне Telegram) подставляет заглушку-игрока
  `DevTester` и НЕ ходит на сервер — быстро проверять вёрстку/расположение
  HUD без телефона. Финальная проверка серверной логики и реального
  HP/забега — ТОЛЬКО в Telegram (initData не работает в браузере).
- **VPN blocks localhost** — disable during local dev
- **Port 3000 busy?** → `taskkill /F /IM node.exe` then restart server
- **RUN_COST = 3** in `server/src/routes/run.ts` — keep 3 in dev, restore to 10 before release
- **Render sometimes deploys old commit** → always check Events tab after push
- **`git push` деплоит ТОЛЬКО сервер** (Render автослушает пуш). Фронт на
  GitHub Pages деплоится ОТДЕЛЬНО, `npm run deploy` — на этом дважды теряли
  время за сессию, думая, что фронт уже обновился после одного `git push`.
- **Применённую Prisma-миграцию НИКОГДА не редактировать задним числом.**
  Prisma отмечает миграцию по ИМЕНИ папки в `_prisma_migrations`, содержимое
  `migration.sql` после применения не перечитывает — правка уже
  задеплоенного файла молча разойдётся с тем, что реально накатано на
  проде, и следующий `migrate deploy` упадёт с P2022 (колонка/данные не
  совпадают с тем, что Prisma думает уже применено). Нужно другое
  состояние схемы/данных — НОВАЯ миграция поверх, не правка старой.
- **Порядок деплоя при изменении схемы БД**: сначала `cd server && npx
  prisma migrate deploy` (или `migrate dev` локально) против целевой БД,
  ПОТОМ `git push`/`npm run deploy` кода, который на эту схему рассчитан.
  Обратный порядок — рабочий код, ждущий колонку/данные, которых ещё нет.
- **Перед ЛЮБОЙ диагностикой "не работает" — сначала проверить, что реально
  развёрнуто** (какой коммит на Render, обновлялся ли GitHub Pages, см.
  два пункта выше). Характерный симптом путаницы со старым фронтом: сервер
  честно отвечает 200 с правильными данными, а в Telegram ничего не
  меняется — потому что открыт старый закэшированный клиент, а не потому
  что сломан сервер.
- **Перед деплоем сервера** прогонять ОБЕ сверки ручных копий (обе read-only,
  по sha256, сами ничего не чинят):
  `python tools\check_map_sync.py` — `public/assets/maps/*_slots.json` против
  `server/src/maps/*_slots.json`;
  `python tools\check_potion_sync.py` — `src/potions.ts` против
  `server/src/potions.ts` (каталог зелий обязан совпадать БАЙТ В БАЙТ).
  Копии реально расходятся, если правили только одну сторону — так уже было
  21.09.2026, когда `MAX_POTIONS_PER_PURCHASE` добавили сперва в серверную
  копию (серверная и клиентская части фичи шли разными коммитами).
- **Откуда в Telegram Mini App брать safe-area: НЕ из `env()`.** Проверено
  29.09.2026, три источника, и рабочий ровно один.
  1. `env(safe-area-inset-bottom)` у нас **всегда 0**: в `index.html` у
     `<meta name="viewport">` нет `viewport-fit=cover`, а без него браузер не
     отдаёт insets вообще — ни на iOS, ни на Android. Пока cover не добавят, все
     `env(safe-area-*)` в проекте (включая HUD-плиту) — нули.
  2. `--tg-safe-area-inset-*` / `--tg-content-safe-area-inset-*` — переменные
     СОБСТВЕННОГО скрипта Telegram (`telegram-web-app.js`). Проект его не грузит
     (работает через `@telegram-apps/sdk`), поэтому их тоже нет.
  3. Рабочий источник — переменные САМОГО SDK, и имена у них ДРУГИЕ:
     `--tg-viewport-safe-area-inset-bottom` и
     `--tg-viewport-content-safe-area-inset-bottom`. Они появляются ТОЛЬКО после
     `bindViewportCssVars()` (вызывается в `main.tsx` после `mountViewport()`);
     до 29.09.2026 этого вызова в проекте не было вовсе.
  Отступ считается как `calc(16px + max(env(...), var(--tg-viewport-...), ...))`:
  `max`, а НЕ сумма — источники меряют одно и то же, сложение дало бы двойной
  отступ там, где доступны сразу два. Значения SDK приходит с единицами
  (`${n}px`), иначе `max()` стал бы невалидным и правило отвалилось бы целиком.
- **Высоту контейнера под фоновую картинку задавать ЯВНО** (`calc()` от
  известной ширины, ИЛИ `padding-bottom: <aspect>%` на обёртке) —
  auto-высота от `<img>` не даёт родителю определённую высоту, и проценты
  `top`/`height` у абсолютно спозиционированных детей внутри считать не от
  чего (тихо превращаются в 0/auto). Наступали на это ДВАЖДЫ в почти
  идентичной форме: HP-плита (`HP_FRAME_H`) и плита итогов забега
  (`results_plate.png`, паддинг-боттом трюк) — оба раза чинилось одним и
  тем же приёмом.
- **`transform: scale()` уменьшает КАРТИНКУ, но НЕ бокс в раскладке — и этим
  делает страницу шире экрана.** Стоило целой сессии поисков «почему магазин
  двигается вбок». Якорь сцены «убежище» (`App.tsx`) — `position:absolute` без
  размеров, с одним ребёнком шириной 502px, ужатым `scale(0.42)`. Ширину якорь
  брал ПО СОДЕРЖИМОМУ, то есть 502px: на 375px он занимал 172.5…674.5 и торчал
  за правый край на 299.5px, на 390 — 291.4px, на 320 — 329.2px. Видно его не
  было (внутри всё смещено трансформом, сам div пустой и `pointer-events:none`),
  но документ становился шире экрана, страницу можно было таскать вбок, и со
  сдвинутым скроллом ЛЮБОЙ экран выглядел обрезанным справа — включая третий
  столбец витрины магазина, который сам по себе был в порядке.
  Лечится размером самого якоря: `width: 0; height: 0`. Это ТОЧКА привязки,
  ребёнок позиционируется своим `translate(-50%,-100%)`, и его положение от
  ширины родителя не зависит — картинка не двигается.
  ⚠️ `overflow-x: hidden` на body в таких случаях — НЕ решение: он прячет
  симптом вместе с обрезанным содержимым, и настоящая причина остаётся.
  ⚠️ Как искать такое вообще: не чтением кода, а ЗАМЕРОМ. Собранный фронт
  открывается в headless-Chrome внутри iframe нужной ширины, и по всем элементам
  собирается `getBoundingClientRect().right > innerWidth`. Chrome и Edge на
  машине есть; `--window-size` ширину не даёт (окно не сжимается ниже ~500px),
  поэтому ширину задаёт именно iframe.
- **Колонки сетки с фиксированным числом — ВСЕГДА `minmax(0, 1fr)`, никогда
  `1fr`, если внутри картинка.** `1fr` это `minmax(auto, 1fr)`, а грид-элемент в
  треке с авто-минимумом получает `min-width` ПО СОДЕРЖИМОМУ; у `<img>` это его
  ИНТРИНСИК-ширина, потому что `width:100%` при расчёте min-content считается за
  `auto`. Иконки в проекте 128×128, поэтому ячейка витрины требовала 142px, три
  колонки — 442px, а на 375px (iPhone) колонкам достаётся 311px: третья колонка
  уезжала за правый край на 131px, и её просто не было видно. Ошибка молчит на
  широком экране и в браузере на десктопе — ловится только узким.
  `minmax(0, …)` лечит это не «зажимом», а тем, что авто-минимум элемента при
  нулевом минимуме трека НЕ ПРИМЕНЯЕТСЯ вовсе (CSS Grid §6.6), и картинка
  сжимается вместе с ячейкой. Наступали ДВАЖДЫ: в сетке инвентаря (там
  `minmax(0, 1fr)` стоит с самого начала) и в витрине магазина, написанной
  позже независимо. С 28.09.2026 ВСЕ сетки в `App.tsx` переведены на
  `minmax(0, 1fr)` — исключений нет намеренно, чтобы правило не нужно было
  вспоминать по наличию картинки.
- **Удаление колонки в проде — ВСЕГДА две миграции, не одна.** Сначала
  `add` (новые колонки + переливка данных), выкладка нового сервера,
  проверка вживую — и только отдельным заходом `drop`. Одной миграцией
  нельзя: Prisma перечисляет колонки в `SELECT` поимённо, а деплой на Render
  не мгновенный, поэтому ещё живой старый процесс начинает падать на каждом
  чтении персонажа, то есть на ЛОГИНЕ, у всех сразу. Проделано на
  `potionCharges` → `potionT1..T5` (`20260911120000_potion_tiers_add` +
  `20260911130000_potion_charges_drop`).
- **Папку `drop`-миграции нельзя создавать заранее, «чтобы была».**
  `prisma migrate deploy` применяет ВСЕ pending-миграции разом, так что
  заготовленная папка сработает на ближайшем же деплое и уронит логин ровно
  так, как две миграции и должны были предотвратить. Создавать её — вторым
  заходом, непосредственно перед применением.
- **Шипы vs габарит игрока: инвариант, который перевернётся МОЛЧА.** Урон
  шипов меряется по ЗАМЕРЕННОЙ макушке спрайта
  (`SPIKE_BODY_TOP_GROUND = 3.73` / `SPIKE_BODY_TOP_AIR = 31.85`,
  `constants.ts`), а не по верху бокса `phys.y` — бокс выше настоящей головы,
  и разброс зависит от позы (в прыжке ноги поджаты, якорь смещён, см.
  `RISE_ANCHOR_Y`/`FALL_ANCHOR_Y`). Отсутствие бага держится на неравенстве
  `JUMP_HIT_OFFSET_Y − TILE_SIZE*PLATFORM_H_RATIO − SPIKE_BODY_TOP_AIR <= 0`,
  сейчас `40 − 28.16 − 31.85 = −20.01` (запас 20px). Сменят спрайт героя или
  поднимут высоту прыжка — знак перевернётся, и шип на узкой платформе `'='`
  снова начнёт бить по воздуху над головой, БЕЗ падений и ошибок. Рецепт
  перезамера обеих констант — в комментарии к ним в `constants.ts`.
- **Анти-чит-потолки ломаются молча при смене формы данных.** Потолок
  полученного урона считался как `run.potions * 0.25`, где `potions` был
  скаляром. При переходе на массив по тирам выражение не упало бы — оно
  дало бы `NaN`/мусор и начало РЕЗАТЬ рост выносливости у честных игроков.
  Пересчитано на `run.sips × максимальный healFrac по каталогу`. Правило:
  меняя форму поля в `currentRun`, отдельно проверять все анти-чит-формулы,
  которые его читают.

- **Цикл `while` со сравнением чисел — потенциальное ЗАВИСАНИЕ ВСЕГО
  СЕРВЕРА, если в него попадёт нечисло.** Найдено 21.09.2026 в
  `applyStatProgress` (`game.ts`): условие выхода было `if (progress <
  threshold) break`, а на `NaN` ложны ОБА сравнения — цикл не вышел бы
  никогда, вычитая порог из `NaN` и наращивая стат. Node однопоточен, так
  что это не «медленный запрос», а мёртвый сервер для всех. Починено
  отрицанием: `if (!(progress >= threshold)) break` — нечисло выходит на
  первой же итерации. Источник `NaN` закрыт отдельно, в `clampRunProgress`
  (`run.maxHp` из испорченного `currentRun` приводится явно), но защита в
  самом цикле ОБЯЗАТЕЛЬНА: через `applyStatProgress` проходит `/auth/login`,
  то есть запрос, без которого игра не открывается вообще, и он обязан
  выжить при любом содержимом `currentRun`. Правило на будущее: в цикле,
  условие которого зависит от пришедшего снаружи числа, выход пишется
  отрицанием.
- **`refreshPlayerFromServer` в `App.tsx` — это ПОЛНЫЙ ВХОД
  (`loginWithTelegram`), а не «обновить профиль»: он закрывает открытый на
  сервере забег (подтверждённый — как смерть, со сгоранием всего банка
  трофеев). Для сверки золота и склада есть `GET /character/profile`, который
  не пишет ничего — только он и годится для кнопок вида «Обновить баланс».**
- **Пометка в `currentRun`, которую должен снимать клиент, выкладывается
  ТРЕТЬИМ шагом: сначала сервер с эндпоинтом, потом клиент, который его
  зовёт, и только потом сервер, который начинает ставить пометку.** Любой
  другой порядок означает, что живой клиент пометку не снимает — а у
  «неподтверждённого» забега цена этого в том, что брошенный забег
  закрывается без штрафа, то есть убить приложение становится выгоднее
  смерти. Проделано 21.09.2026: `2414aee` → `6a6beb6` (Pages 01:52) →
  `396fab3` (Render 01:59).
- **`fetch` без таймаута в WebView может не завершиться ВООБЩЕ.** В
  авиарежиме на телефоне запрос не отдаёт ни ответа, ни ошибки: промис не
  резолвится, `catch` не выполняется, и любая обработка ошибки — плашка,
  статус, очередь — молчит, хотя написана верно. Стоило одной провальной
  проверки: плашка "глоток не сохранён" не появлялась именно поэтому.
  Лечится только `AbortController` + бюджет на весь вызов. Сейчас таймаут
  есть у `recordSip` (4 с попытка / 12 с бюджет), `finishRunExplore`
  (20 с / 60 с, больше — сервер на Render Free просыпается из сна; повторяет
  не только 5xx, но и 409 `Run state changed, retry` — гонку за `currentRun`,
  которую финиш теперь отдаёт вместо тихой перезаписи) и
  `recordProgress` (4 с, БЕЗ повторов — следующий срез несёт накопленное и
  перезаписывает потерянный). У остальных запросов (`startRunExplore`, вход,
  покупка, инвентарь, экипировка, скиллы) таймаута НЕТ — см. открытые задачи.
- **`npm run deploy` кладёт сборку в ветку `gh-pages` и НЕ пушит `main`.**
  Клиентские коммиты после деплоя могут остаться только локально, и
  следующая сессия увидит на GitHub старый код. Проверять
  `git log origin/main..main` в начале и в конце сессии (дополняет пункт
  про «`git push` деплоит ТОЛЬКО сервер» выше).
- **`"level":30` в логах Render — это severity записи Pino, а НЕ уровень
  персонажа.** 30 = info. Ушло время на «почему у всех 30 уровень».
- **Инлайн-стиль на кнопке, чью `cssText` переписывает функция-реф, стирается
  на каждом рендере.** Подсветку нажатия и расширение зоны захвата задавать
  ПРАВИЛОМ таблицы стилей по атрибуту (`data-pressed`, `::after`) с
  `!important`, а не `style`. Наступали дважды: подсветка 8 боевых кнопок и
  зона захвата ▲ (`PRESS_CSS`, `TouchControls.tsx`).
- **Реальный радиус боевой кнопки на 1 px БОЛЬШЕ номинальной константы** —
  `box-sizing: content-box` плюс рамка 1 px: ▲ 29 вместо `JMP_R` 28, веер 23
  вместо `BTN_R` 22. Любой расчёт зазоров по одним константам ошибается на
  эту рамку, и ошибка тем опаснее, чем теснее раскладка: центры ▲ и 🔄 стоят
  в 58.03 px, зона захвата ▲ (`::after { inset: -6px }`) даёт радиус 34,
  значит зазор до 🔄 = 58.03 − (34 + 23) = **1.03 px**, а не 2.03, как выйдет
  по константам без рамок. Веер расширять нельзя вовсе: хорда между его
  соседними кнопками ровно `2·BTN_R`, любое расширение — сразу наложение.
- **Смертей в забеге ДВЕ, и они не взаимозаменяемы.** Обе ведут в один
  `triggerDeath()`, но приходят по разным путям, и путать их нельзя:
  1. **По здоровью** — `takeDamage()` → `hp <= 0` (`Explore.tsx`). Через неё
     идут ВСЕ источники урона: враг, ближний бой босса, его шипы и волны, шипы
     карты, ловушка-мимик. Здесь же живут все перехваты: debug-бессмертие,
     i-frames рывка, окно оберега, броня, округление урона.
  2. **Скриптовая** — `killPlayer()`, обнуляет hp НАПРЯМУЮ, минуя `takeDamage`,
     а значит и броню, и рывок, и оберег. Источник сейчас один: провал таймера
     обелиска.
  ⚠️ Поэтому любой «спасатель от смерти» врезается в ветку `hp <= 0` внутри
  `takeDamage`, а НЕ в `triggerDeath`: во втором случае он молча начнёт спасать
  и от обелиска, то есть отменит скриптовую смерть, которую дизайн задумал
  неотменяемой. Так сделан оберег от смерти (28.09.2026). Появится второй
  источник скриптовой смерти — он унаследует это поведение автоматически, и это
  верно; захотят обратного — решение дизайнера, не правка по месту.
- **Игровое окно, заданное в миллисекундах, тикает по `ticker.deltaMS`, а не
  по кадрам.** По кадрам оно на просевшем FPS укорачивается в реальных
  секундах — игра ужесточается ровно там, где и так тяжело.
- **Окно койот-тайма обязано гаситься в ветке самого прыжка.** Без этого оно
  переживает прыжок и даёт второй в воздухе: койот молча превращается в
  двойной прыжок.
- **Урон округляется `Math.ceil`, HP — `Math.round`.** Округление урона
  никогда не идёт в пользу игрока.
- **`character` в ответе `/auth/login` показывает состояние ПОСЛЕ закрытия
  забега только потому, что каждое записанное поле руками отражено обратно в
  объект `char`.** Ветка закрытия (`routes/auth.ts`) пишет в БД одним
  `update`, а в ответ уходит `...charFields` — то есть ПРОЧИТАННЫЙ до записи
  персонаж. Сходится это лишь благодаря строкам вида `char.trophies = 0`,
  `char.potionT1..T5 = newPotionStock[...]`, `char.strength = growth.strength`,
  `char.energy = refund.energy` — по одной на каждое записанное поле.
  Добавили в `update` новое поле и не продублировали присваивание в `char` —
  клиент молча получит СТАРОЕ значение: типы совпадают (это то же поле той же
  модели), сборка и тесты промолчат, а в игре разойдутся число на экране и
  число в БД. Правило: правка ветки закрытия забега — это ВСЕГДА две строки
  на поле, запись и отражение.
- **Общего пакета между клиентом и сервером НЕТ** (`tsconfig.app.json`
  включает только `src`, у сервера `rootDir "./src"`), поэтому всё общее
  скопировано РУКАМИ. Полный список копий — сверено по коду, менять только
  парами:

**Формула трофеев на финише** (`/run/finish-explore`, сверено по коду):

```
bank   = character.trophies            // банк ДО забега = банк на СТАРТЕ:
                                       // за открытый забег трофеи в БД не меняет
                                       // ничто (сверено по всем записям server/src)
closed = parseClosedEventIndices(body.closedEvents, run)
deal   = readSmugglerDeal(run)         // none | deal | malformed
                                       // malformed -> 500 Corrupt run state,
                                       // молча считать «как без сделки» нельзя

сделка есть:                           // множитель уже применён в момент сделки
    posle = Σ trophyReward событий из closed, которых НЕТ в deal.closedBefore
            (событие Контрабандиста исключается)
    total = deal.after + posle         // закрытое ДО сделки второй раз не считается —
                                       // оно уже внутри deal.stake
сделки нет:
    total = bank + Σ trophyReward всех closed (кроме Контрабандиста)

newTrophies  = total
earned       = total − bank            // ⚠️ МОЖЕТ БЫТЬ ОТРИЦАТЕЛЬНЫМ
trophiesLost = died ? bank : 0         // как и раньше: смерть жжёт весь предрановый банк
запись в БД  = trophies: died ? 0 : newTrophies
```

⚠️ **`trophiesEarned` в ответе может быть ОТРИЦАТЕЛЬНЫМ и нулём НЕ обрезается.**
Так выглядит кража у Контрабандиста, когда итог меньше банка на старте (ставка =
банк + добыча до сделки, множитель кражи 0.5). `Math.max(0, …)` здесь был бы
тихим фолбэком: он спрятал бы от игрока самую дорогую новость. Экран итогов это
умеет — при `trophiesEarned < 0` подпись становится «ТРОФЕЕВ ПОТЕРЯНО», а число
берётся по модулю (`trophyLossView` в `ResultsScreen`, `Explore.tsx`; та же
логика скопирована в `PastRunNotice.tsx`, там пометка «менять вместе»).

⚠️ **При смерти `trophiesEarned` означает НЕСОСТОЯВШИЙСЯ прирост**, а не
полученное: поле считается до обнуления и остаётся в ответе как есть. Экран
итогов его при `died` НЕ показывает — там своя величина, `trophiesLost` (весь
сгоревший банк). Читать `trophiesEarned` на смерти как «сколько игрок получил»
нельзя; до 27.09.2026 оно там значило добычу забега, теперь — прирост, который
сгорел вместе с банком.

Пишет его по-прежнему НИЧТО, и источника удачи в игре нет (её даёт только амулет, а надетые предметы в этот расчёт не входят), поэтому у живого игрока множитель пока всегда ровно 1. Формула заведена сразу, чтобы появившийся источник удачи не требовал второй правки дропа.

**`currentRun` shape** — один вид, старого 3-комнатного потока больше нет:
`{ mode:'explore', mapFile, events, hp, maxHp, potions, sips, potionsDrunk?, progress? }` (Phase 2.5) — `events` несёт полный розыгрыш (trophyReward/isMimic), клиенту наружу не идёт целиком (см. Phase 2.5).
`potions` — снимок склада ПО ТИРАМ на старт, `sips` — лимит глотков за забег, `potionsDrunk` — выпитое по тирам, пишет `/run/sip` по глотку. Поля `potionsDrunk` нет у забега без глотков и у начатых до появления `/run/sip` — читать ТОЛЬКО через `readRunPotionsDrunk` (нет поля = нули, испорчено = громкий 500, а не счёт с нуля).
`progress` — срез четырёх сырых счётчиков забега, пишет `/run/progress` заменой; читать ТОЛЬКО через `readRunProgress` (нет поля = нули, испорчено = null и громкий warn).
`consumablesUsed` — список id расходников, ВЗЯТЫХ в этот забег (пишет
`/run/start-explore` вместе со списанием склада, дальше только читается). Поля
нет — не брали ничего. Список id, а не количеств: повторы в гнёздах запрещены,
каждый взятый ровно один. Читать ТОЛЬКО через `readConsumablesUsed`
(`runState.ts`) — три состояния `none`/`used`/`malformed`, как у `smugglerDeal`:
свалить «нет поля» и «испорчено» в пустой список значило бы тихо отменить уже
списанный расходник, то есть отобрать у игрока купленное. Валидатор ПЕРЕПРОВЕРЯЕТ
то же, что проверял старт (каталог, флаг `runSlot`, повторы, потолок): колонка
`Json?` схемой не проверяется, и испорченный извне список не должен дать эффект,
которого игрок не покупал.
`smugglerDeal` — сделка с Контрабандистом, если она была: `{closedBefore, stake,
outcome, after}`. Пишется ОДИН раз (`POST /run/smuggler-deal`) и дальше только
читается — бросок неповторим. `closedBefore` нужен финишу, чтобы отделить добычу
ДО сделки (она уже внутри `stake` и умножена) от добычи ПОСЛЕ (прибавляется без
множителя); `after` хранится готовым числом, а не пересчитывается на финише —
пересчёт по константам разошёлся бы с тем, что игрок увидел, если константы
поменяют посреди живого забега. Читать ТОЛЬКО через `readSmugglerDeal`
(`runState.ts`), и он возвращает ТРИ различимых состояния — `none` / `deal` /
`malformed`: свалить «сделки не было» и «поле испорчено» в один `null` значило бы
тихо отменить кражу или отнять выигрыш.
`confirmed` — увидел ли игрок забег (ставит `POST /run/ready`, а также первый глоток и первый срез: любая реальная игра). `spentEnergy` — сколько энергии списал старт ИМЕННО этого забега, чтобы вернуть её при закрытии без штрафа. Читать через `readRunConfirmed`/`readRunSpentEnergy`; **нет поля `confirmed` = подтверждён** (все забеги до фичи такими и были), испорчено = тоже подтверждён + `log.error`: обратная трактовка сделала бы порчу `currentRun` выгодной. Решение «штрафовать или нет» целиком в чистой `judgeInterruptedRun`. Форма `currentRun`, её валидаторы, потолки роста статов и раскладка склада зелий по колонкам живут в **`server/src/runState.ts`** — общем модуле: тот же JSON читают и `routes/run.ts`, и `routes/auth.ts`, а колонка `Json?` схемой не проверяется, поэтому второй валидатор рядом разъехался бы молча. Сама формула роста (`applyStatGrowth`) переехала в `game.ts` по той же причине — вызывающих стало два.
⚠️ Новые поля внутри `currentRun` миграции НЕ требуют — колонка `Json?`.

## Stat & Leveling System

Полностью переписано (см. `server/src/game.ts`) — старая экспоненциальная
нормализация урона по уровню (`base*growth^(stat-10)`,
`normalizeDealt/ReceivedDamage`) и старый инкрементальный левелинг
(`checkStatLevelUp`, `LEVELUP_*_GAIN`, поля `strengthAtLevelUp`/
`enduranceAtLevelUp`, скрипт `fix-level-snapshots.ts`) — УДАЛЕНЫ, в коде и
в схеме их больше нет.

### Growth (IMPLEMENTED) — `applyStatProgress`, `game.ts`
Порог до следующей единицы стата растёт от самого стата (не от уровня):
```
порог(стат) = round(база * (стат/10)^STAT_THRESHOLD_EXPONENT)
STAT_THRESHOLD_EXPONENT = 1.2
```
База своя на канал: `STRENGTH_THRESHOLD_BASE=710`,
`ENDURANCE_THRESHOLD_BASE=290`, `AGILITY_THRESHOLD_BASE=710`. Прогресс —
RAW урон/лечение без какой-либо нормализации по уровню: сила растёт от
`attackDamageDealt`, выносливость от `damageTaken`, ловкость от
`skillDamageDealt + healedAmount`. Копится в `strengthProgress`/
`enduranceProgress`/`agilityProgress` (Float), при пересечении порога — `stat++`,
остаток переносится (цикл `while`, может перепрыгнуть сразу несколько
уровней на один большой урон).
- Attack damage = `15 + Math.floor(strength / 2) + damage надетого оружия + 2 × купленных закалок клинка` —
  ЕДИНСТВЕННАЯ формула на весь клиент, `playerAttackDamage` в
  `src/playerDamage.ts`. Её зовут и строка "Урон" на экране "Персонаж", и
  забег (`Explore.tsx`, фиксирует значение ОДИН раз в начале `setup()`, до
  `/run/start-explore`). Раньше формула была записана двумя одинаковыми
  текстами в двух местах, и оружие не входило ни в одну. Урон оружия
  неизвестен (инвентарь не 'ready') — забег НЕ стартует и показывает
  причину, тихого нуля нет. Скиллы этой формулой не пользуются — они бьют
  долей maxHp цели, это отдельное решение. Сервер урон игрока не считает.
  Исходное правило дизайна, из которого выведено `floor(strength / 2)`:
  **2 силы = +1 урона**. Формула ему соответствует — менять коэффициент,
  не пересогласовав правило, нельзя.
- **Ловкость должна влиять на скиллы ПО-РАЗНОМУ** (решение дизайнера,
  `docs/archive/otvet2.txt`): у одного скилла это прибавка урона, у другого
  — эффективность, у третьего — сила статус-эффекта. То есть будущая связь
  «ловкость → скиллы» это НЕ один общий множитель урона на все пять, а своя
  зависимость на каждый. Сейчас не реализовано вовсе (см. открытые задачи):
  ловкость растёт ОТ использования скиллов, но обратно на них не влияет.

### Leveling — `calculateLevel`, `game.ts`
Уровень — ЧИСТАЯ функция текущих статов, никакой истории/снапшотов:
```
calculateLevel(strength, agility, endurance, bonusLevels):
  канал_урона     = floor((сила + ловкость - 20) / 6)
  канал_живучести = floor((выносливость - 10) / 3)
  уровень = 1 + max(канал_урона, канал_живучести) + bonusLevels
```
Два независимых канала (атака+ловкость vs выживание) — какой дальше ушёл,
тот и определяет стат-часть уровня. `bonusLevels` — счётчик уровней НЕ от
статов, только инкрементируется дискретными событиями (сейчас источник
один: убийство босса, +1). Колонка `Character.level` в БД осталась как
денормализованный снимок для аналитики/отладки — сама логика её НИГДЕ не
читает, только пишет (после каждого пересчёта статов).

Темп (по формуле, не с потолком): ~5 забегов до 2 уровня, ~23 до 100, ~28
до 500. Замедление плавное, жёсткого потолка нет.

## Economy
- Trophies = risky currency. Копятся МЕЖДУ забегами (не сгорают по одному
  забегу), стираются ТОЛЬКО смертью (весь банк целиком, см.
  `/run/finish-explore` в Architecture выше) — abandon по кнопке
  выхода тоже засчитывается как смерть, отдельного "тихого" выхода без
  потери нет. ЕДИНСТВЕННОЕ исключение (21.09.2026) — забег, который игрок
  вообще не увидел (неподтверждённый, см. `POST /run/ready` и Design
  Decisions, вариант А): он закрывается без потери банка, и это не «тихий
  выход», а отказ штрафовать за несостоявшийся забег.
- Gold = stable, used for potions (20 gold each). Обмен трофеев на золото —
  ТОЛЬКО между забегами (в меню), **РЕАЛИЗОВАН 27.09.2026**: вкладка «Обмен» в
  магазине → `POST /character/exchange-trophies`, курс `TROPHY_GOLD_RATE = 1`
  (1 трофей = 1 золото), обмен только ПОЛНЫЙ — весь банк разом, частичного
  нет. Внутри забега обмен запрещён (400 `Run in progress`): банк там ещё
  может сгореть смертью или вырасти финишем. Подробности — `docs/shop.md`,
  раздел «Обмен трофеев на золото», и Architecture выше.
  Курс живёт ТОЛЬКО на сервере; клиент получает его полем `trophyGoldRate`
  (ответ логина и `GET /character/profile`) и своей копии не имеет — см.
  примечание под таблицей копий клиент/сервер выше.
  Второй, СОВСЕМ ДРУГОЙ обмен трофеев — у Контрабандиста ВНУТРИ забега, ×1.5
  при удаче / кража половины при провале. Не путать: другая механика, другая
  валюта на выходе (трофеи, а не золото) и своя открытая задача — он обязан
  умножать БАНК + ДОБЫЧУ ЗАБЕГА, а сейчас умножает только добычу (см. Next
  Steps, [КОНТРАБАНДИСТ], там пример в числах).
- Potions: ПЯТЬ ТИРОВ, у каждого своя сила лечения и уровень открытия —
  каталог `src/potions.ts` (10/15/20/25/30% от maxHp, ур. 1/5/10/20/30, цена
  20/45/90/160/280). Запас свой на каждый тир (`Character.potionT1..T5`).
  `currentRun.potions` — снимок склада ПО ТИРАМ на старт забега,
  `currentRun.sips` — лимит глотков за забег (`MAX_SIPS_PER_RUN = 3`, но не
  больше суммы запаса). Пьётся всегда СТАРШИЙ доступный тир, кончился —
  следующий вниз прямо внутри забега; иконка на кнопке HUD показывает, что
  выпьется следующим.

      (3) итоговый банк после забега совпадает с формулой (Architecture выше) —
      сверять с числом на экране «Персонаж» ПОСЛЕ забега, а не с всплывашками
      (они клиентские, см. задачу [НАГРАДЫ, расхождение]).
      Проверено только сборкой и арифметикой на 7 случаях.

    Два пункта, раньше стоявших здесь как риски, СНЯТЫ — на оба ответ дан
    в дизайне (см. Design Decisions ниже): смерть ради выносливости не
    выгодна по построению, а разрыв между `bonusLevels` и стат-уровнем —
    задуманная разница билдов, а не перекос. Проверять игрой остаётся
    только темп.

## Design Decisions

### Прокачка и баланс — принятые решения (не риски)

Ответы дизайнера, перенесены из `docs/archive/otvet2.txt`. Это решения с
причиной: не переоткрывать их как вопросы.

- **Уровень от босса НЕ делает персонажа сильнее — так задумано.** Босс
  даёт доступ к наградам, но не к силе; кто копит уровни боссами и
  забивает на статы, будет буксовать и об обычных врагов, и об будущих
  боссов (враги масштабируются от уровня игрока). Это не перекос, который
  надо чинить.
- **Разные пути прокачки — ФИЧА, а не баг.** Охотник на боссов и гриндер
  статов придут к 20 уровню с разными билдами и разной силой. Разнообразие
  билдов считается плюсом.
- **Выносливость растёт от ПОЛУЧЕННОГО урона намеренно, и это не эксплойт.**
  Фармить урон смертями невыгодно по построению: трофеи — основная валюта
  прогресса, при смерти сгорают целиком, а забег кончается сразу. Игрок,
  умирающий ради выносливости, платит за это прогрессом.
- **Anti-mastery признан и принят.** Умелый игрок получает меньше урона и
  качает выносливость медленнее — это ок: HP растёт и другими системами.
- **Цели баланса скиллов** (формул пока нет, цели есть): бой остаётся
  сложным всю прогрессию; игрок никогда полностью не перерастает контент;
  скиллы можно улучшать; прогрессия скиллов — с УБЫВАЮЩЕЙ отдачей; весь
  контент не съедается за один день.
- **Философия босса**: босс должен ощущаться редким и ценным. Награда —
  уровень сразу, трофей босса и ПОСТОЯННАЯ награда к стату (в коде сейчас
  первые две, третья — предмет-«сердце», см. открытые задачи).
- **Сначала MVP, баланс потом.** Точная скорость прокачки до 20 уровня
  сознательно не фиксировалась — настраивается плейтестами.
- **Реролл событий защищать не планируется.** Цены уже есть: энергия на старт
  забега, потеря трофеев при смерти и при выходе, 20% шанс кражи. Этого
  достаточно.
  ⚠️ **ОБНОВЛЕНО 27.09.2026: «эксплойт контрабандиста» из этой строки УШЁЛ —
  его больше нет.** Речь шла о том, что исход обмена сообщал клиент, а сервер
  верил на слово. Теперь бросок серверный (`/run/smuggler-deal`), и защищать
  тут нечего. Незащищённым остаётся другое и более общее — СОСТАВ списка
  закрытых событий, который клиент называет сам (см. Next Steps,
  [БЕЗОПАСНОСТЬ]); это часть нерешённого вопроса об авторитетности боя, а не
  отдельное решение «не защищать».
- **Модель сетевой авторитетности боя НЕ выбрана** — выбирается по
  безопасности, анти-читу, производительности и ограничениям Mini App.
  Де-факто сейчас бой целиком на клиенте, а сервер ставит потолки
  (см. `clampRunProgress`, анти-чит-потолки в Critical Gotchas) и верит клиенту
  в том, КАКИЕ события закрыты (`closedEvents` — и на финише, и в сделке с
  Контрабандистом). Исходу обмена сервер с 27.09.2026 больше не верит — бросает
  сам. Всё это следствие отсутствия решения, а не само решение.
- ⚠️ **ОТМЕНЕНО: прежний замысел «золото менее надёжно, чем трофеи».**
  Сейчас наоборот и это верно: золото стабильно (не сгорает, копится,
  тратится в магазине), рискованная валюта — трофеи (сгорают целиком при
  смерти и при выходе). См. Economy выше; строка из `otvet2.txt` описывает
  старую экономику и перенесена НЕ была.

Всё, что в `docs/archive/otvet2.txt` разошлось с кодом (комнаты и их
шансы, Trap Room, зелье на 50% maxHp, тиры экипировки до 50 уровня,
перчатки на силу/ловкость), намеренно оставлено только в архиве.

### Прочее
- Puzzle = game-mechanics quiz
- Heal/potions don't affect Endurance growth (totalDamageTaken tracked separately)
- actualHpLost sent to server for correct HP carry between rooms
- Enemy base stats: normal 120HP/14dmg, boss 200HP/18dmg
- Wide arena (3000px) with camera follow
- Флип по направлению в Explore ГОТОВ и разный для героя/зверя (проверено на
  реальных ассетах, не общее правило "sprites face left by default"): герой
  смотрит ВПРАВО по умолчанию (facing===1 → без зеркала, facing===-1 →
  scale.x в минус), зверь смотрит ВЛЕВО по умолчанию (facing===-1 → без
  зеркала, facing===1 → scale.x в минус) — см. "Спрайты героя"/"Спрайты и
  боевая логика зверя" выше. В Battle.tsx (старая боевая сцена) этот флип
  ещё не переносился — там актуальность прежнего допущения не проверялась.
- **Тихие фолбэки — запрещены, делать их громкими.** `?? 10`,
  `if (!x) return` и подобное молча подставляют правдоподобное, но ложное
  значение вместо явного сигнала "данных нет" — баг маскируется, а не
  чинится, и стоит времени на отладку (реальный случай — фолбэк на
  экране "Персонаж", который тихо показывал `10` вместо настоящей брони,
  когда `inventory` ещё не успел загрузиться; чинили explicit guard'ом
  "данные недоступны" вместо тихого числа). Тот же принцип — за фолбэком
  без токена в Explore (см. "Единый источник тройки событий" выше):
  оффлайн-заглушка розыгрыша событий ОСТАВЛЕНА (нужна для UI-отладки без
  Telegram), но помечена ВИДИМОЙ оранжевой плашкой на экране, а не тихо
  подменяет данные неотличимо от настоящего забега.
- **Обрыв связи в забеге — вариант А, ПРИНЯТО.** Свернул приложение — игра
  замирает в памяти и продолжается сама при возврате, ничего специально
  делать не надо (проверено вживую). Закрыл приложение полностью — забег
  закрывается как смерть: при следующем входе показывается экран итогов,
  трофеи сгорают.
  ⚠️ **УТОЧНЕНО 21.09.2026: это верно для ПОДТВЕРЖДЁННОГО забега** — того,
  который игрок реально увидел (клиент прислал `POST /run/ready`, либо успел
  ударить/выпить). Забег, брошенный ДО показа (упала текстура, оборвалась
  сеть, убили приложение на экране «ПОДГОТОВКА»), закрывается БЕЗ штрафа:
  трофеи, зелья и статы не трогаются, энергия возвращается. Это не смягчение
  правила, а его же применение: штрафовать за забег, которого игрок не видел,
  значит наказывать за сбой загрузки, а не за побег от смерти. Само правило
  «закрыть приложение никогда не должно быть выгоднее, чем умереть» остаётся
  в силе и защищено с двух сторон — признаком реальной игры (любой удар или
  глоток закрывает забег обычным, штрафным путём) и трактовкой любого
  сомнения против игрока (испорченное поле = подтверждён).
  Никакого промежуточного сохранения состояния забега НЕ
  делаем. Причина отказа: любое сохранение, которое откатывает игрока
  назад при переоткрытии, делает закрытие приложения выгоднее смерти
  (закрыл перед боссом на низком HP — получил бесплатный ретрай). Правило
  на будущее: закрыть приложение никогда не должно быть выгоднее, чем
  умереть в забеге. Плюс варианта А — сам момент закрытия ловить не нужно
  вообще: сервер видит открытый `currentRun` при следующем входе и
  закрывает его сам.
