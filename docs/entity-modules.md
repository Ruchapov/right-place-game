# Модули сущностей Explore — контракт

Вынесено из CLAUDE.md при разбиении документации. Карта всех справочников —
в разделе "Карта проекта" корневого CLAUDE.md.

## Модули сущностей (Explore) — контракт

**Правило на будущее**: новые боевые механики Explore НЕ пишутся в
`Explore.tsx` напрямую — отдельным модулем в `src/explore/entities/`.
Готовы три: `skills.ts`, `enemy.ts`, `boss.ts`.

### Контракт

```
createEnemySystem(deps) → { spawn, update(dt, deltaMS), dispose }
createBossSystem(deps)  → { spawn, update(dt, deltaMS), dispose }
createSkillsSystem(deps) → { update(dt), dispose, onAttackStrike, onCastSpawnFrame }
```

- `dt` = `ticker.deltaTime` — кадро-масштабированный, для ДВИЖЕНИЯ (та же
  единица, что у `phys` игрока: `x += vx * dt`).
- `deltaMS` = `ticker.deltaMS` — реальные миллисекунды, для ВСЕХ таймеров
  (кулдауны, hurt/windup, deathHold и т.п.).
- Владение рефами (`enemiesRef`/`bossRef`/`bossSpikesRef`/`bossWavesRef` и
  т.п.) остаётся в `Explore.tsx` — модуль получает их ДЕПОМ, не создаёт
  свои копии. Так `applyAttackHit()` (осталась в `Explore.tsx`, её никто из
  переносов не трогал) продолжает читать/писать те же объекты `Enemy`/
  `Boss`, что и модуль в следующем кадре — без дополнительной проводки.
- Чистые функции из `collision.ts`/`utils.ts`/`rewards.ts` (`isSolid`,
  `sweepFootBlock`, `cellFootBlockTop`, `isPlatformBandBlocking`, `clamp`,
  `rollTrophies`) — модуль импортирует их НАПРЯМУЮ, не депом. Депом
  передаются только closure-функции `setup()` в `Explore.tsx`, которые
  нельзя импортировать (`getPlayerCombatBox`, `pushPlayerOutX`,
  `spawnRewardFloat`, `closeEvent`, `playBossAnim`, `applyBossLayout`,
  `damageEnemy`/`damageBoss`, `applyEnemyHitReaction`/`applyBossHitReaction`
  и т.п.).
- `takeDamage` передаётся ОБЁРТКОЙ `(amount) => takeDamageRef.current(amount)`,
  не самой функцией `takeDamage` — deps собираются один раз при создании
  системы в `setup()`, а `takeDamageRef` синхронизируется отдельным
  `useEffect`'ом на каждый рендер именно затем, чтобы тикер всегда звал
  АКТУАЛЬНУЮ версию функции.
- Ничто внутри `src/explore/` не импортирует из `Explore.tsx` — только в
  обратную сторону. Единственное исключение раньше было временным
  (`PlayerPhysics`/`Enemy`/`Boss`/`EventKind` реэкспортировались из
  `Explore.tsx`, пока типы не переехали в `types.ts`) — сейчас его больше
  нет, все типы приходят из `explore/types.ts`.

**Почему у `skills.ts` `update(dt)` одним параметром.** Не потому, что
"движение скиллам не нужно" (прежняя запись здесь — устарела, снаряды
двигаются). Причина другая: сюда передаётся `ticker.deltaMS`
(`Explore.tsx:3201`), то есть параметр с именем `dt` — это МИЛЛИСЕКУНДЫ, и
второй параметр модулю просто нечем занять. Всё, что модуль считает по
времени, живёт в реальных единицах: кулдауны и таймеры эффектов — в мс,
снаряд шагает в px/СЕКУНДУ (`FIREBALL_SPEED`, внутри `dt / 1000`), как шип
босса. Кадро-масштабированный `dt` понадобился бы для движения ГЕРОЯ, но
рывок двигает героя не модуль, а общий блок физики в тикере `Explore.tsx`
(модуль только решает, что рывок начался).

### `entities/skills.ts` — все пять скиллов РЕАЛИЗОВАНЫ

`createSkillsSystem(deps)` создаётся ОДИН раз в `setup()` (после того как
определены `worldContainer`/`grid`/`getPlayerCombatBox`). Реализованы
**heal, slash, dash, fireball, iceball** — числа, формулы и поведение
каждого см. `docs/skills.md`, здесь только контракт модуля.

**Что возвращает и кто это зовёт:**

| Метод | Кто зовёт | Зачем |
|---|---|---|
| `update(dt)` | тикер, `Explore.tsx:3201` | кулдауны, нажатия, шаг снарядов, урон рывка, тики кровотечения, жизнь ауры/дуги |
| `dispose()` | cleanup эффекта | снять узлы, которые модуль сам добавил в `worldContainer` |
| `onAttackStrike()` | `Explore.tsx:3448` | взмах slash: дуга + выбор цели + наложение кровотечения |
| `onCastSpawnFrame()` | `Explore.tsx:3467` | рождение снаряда fireball/iceball и взведение его кулдауна |

Два последних — это НЕ отдельный вход в модуль "по кнопке", а точки
СИНХРОНИЗАЦИИ С АНИМАЦИЕЙ ГЕРОЯ, которой модуль не владеет:

- `onAttackStrike()` вызывается в ветке анимации атаки, на
  `ATTACK_STRIKE_FRAME`, СРАЗУ после `applyAttackHit()` и под тем же дедупом
  `attackHitDoneRef` — то есть ровно один раз за взмах. На обычном взмахе
  (не slash) это no-op: внутри стоит гейт по пометке "текущий взмах запущен
  скиллом".
- `onCastSpawnFrame()` вызывается в ветке анимации каста, на
  `CAST_SPAWN_FRAME`, под дедупом `castSpawnDoneRef` — ровно один раз за
  каст. Снаряд рождается ЗДЕСЬ, а не по нажатию, и здесь же взводится
  кулдаун снарядного скилла: каст, оборванный раньше этого кадра, кулдаун не
  тратит. Оборвали каст (прыжок/хитстан/смерть сбрасывают `castingRef`) — в
  ветку просто не заходим.

**Как кадры попадают в модуль.** Полем `textures` — нет (прежняя запись
"поле намеренно не заведено" описывала состояние, когда скиллов не было).
Сейчас кадры приходят РЕФАМИ, по одному на лист:
`healAuraFrames`, `slashStreakFrames`, `fireballProjectileFrames`,
`fireballImpactFrames`, `iceballProjectileFrames`, `iceballImpactFrames` —
все типа `MutableRefObject<Texture[] | null>`. Реф, а не готовый массив,
потому что `createSkillsSystem` вызывается в `setup()` РАНЬШЕ, чем
резолвится `loadExploreAssets()` — на момент сборки deps кадров ещё нет (тот
же приём, что `beastFrames` в `enemy.ts`). Модуль каждый раз проверяет
`.current` и, если кадров нет, кричит в консоль ОДИН раз на лист.

Листы `Dash_Strike` и `cast_v2` в deps НЕ передаются и модулю не нужны: это
анимации САМОГО ГЕРОЯ (подмена текстур на его спрайте), ими владеет
`Explore.tsx` (`assets.hero.dash` / `assets.hero.cast`). Модуль в этих двух
случаях только говорит "начни" (`startPlayerDash`/`startPlayerCast`).

Размеры и раскладку листов скиллов сюда НЕ дублируем — единственный
источник: `docs/art-pipeline.md`, раздел "Готовые ассеты — Скиллы (VFX)"
(числа там сверены с заголовками PNG). Эти числа уже дважды разъезжались
между файлами документации, третьей копии быть не должно.

**`equipped` — не заглушка.** Тип поля — `[string | null, string | null]`
(`skills.ts:171`), значение собирается в `Explore.tsx:986-989` из пропа
`equippedSkills?: string[]`, который приходит из `App.tsx`
(`player.equippedSkills`, с сервера: `/auth/login` →
`character.equippedSkills`). Прежняя запись "ЗАГЛУШКА `[null, null]`, Explore
не получает `equippedSkills` пропом" неверна в обеих половинах.

Два состояния, которые нельзя схлопывать (см. комментарий на
`Explore.tsx:979-984`):
- `equippedSkillsKnown === false` — профиль ещё не загружен, данных нет
  вообще: это ОШИБКА, она пишется в консоль один раз за монтирование, кнопки
  показывают `?`;
- `equippedSkillsKnown === true` + `null` в слоте — слот честно пуст
  (игрок волен экипировать 0, 1 или 2 скилла), кнопка просто приглушена.

⚠️ Тип элемента до сих пор `string`, а не `SkillId`. Комментарий у поля
объясняет, что сужение отложено до реализации всех пяти скиллов — **это
условие уже выполнено**, а сужение так и не сделано. Отдельная маленькая
задача: сузить тип и убрать рантайм-список `KNOWN_SKILL_IDS`, который сейчас
нужен только для диагностики (строка в слоте, которой в списке нет —
рассинхрон с сервером, о нём кричит `console.error`).

### `entities/enemy.ts` и `entities/boss.ts` — AI обычного врага и босса, ГОТОВО

Оба вынесены из `Explore.tsx` дословно (та же логика/пороги/тайминги/
порядок проверок, только точки доступа заменены на `deps.*`).
`enemy.ts`: `createEnemySystem(deps) → { spawn, update(dt, deltaMS), dispose }`
— `spawn(tileX, tileY, eventIndex, trophyReward)` пушит нового врага сразу в
`deps.enemies.current` (сам `enemiesRef` остаётся в `Explore.tsx`).
`boss.ts`: `createBossSystem(deps) → { spawn, update(dt, deltaMS), dispose }`
— ОДИН модуль на AI+шипы+волны (не три отдельных — снаряды рождаются AI и
почти полностью пересекаются с ним по deps, разносить по файлам разбирали и
отклонили). `redrawEnemyHpBar`/`redrawBossHpBar` — экспортированы из своих
модулей и импортированы обратно в `Explore.tsx`, т.к. их вызывает
`applyAttackHit()`, которую переносы НЕ трогали ни на строку. А вот
`playBossAnim`/`applyBossLayout` в `boss.ts` НЕ переехали — они читают
`bossRef`/кадры босса через closure `setup()`, и `applyAttackHit()` держит
прямые вызовы к ним по имени; перенести их "по-честному" означало бы
поменять сигнатуру и здесь же переписать `applyAttackHit()` — вместо этого
они переданы в `boss.ts` депом-функцией, как есть.

#### Заслон стана — самое начало обновления сущности

Стан от iceball (`stunTimer` у `Enemy`/`Boss`, длительность
`ICEBALL_STUN_MS`) устроен ЗАСЛОНОМ в начале обновления каждой сущности:
`enemy.ts:292-303`, `boss.ts:320-327`. Пока таймер > 0 — `continue` (у
зверя) / `return` (у босса), то есть ниже не выполняется НИЧЕГО: ни AI, ни
движение, ни гравитация, ни продвижение кадров анимации (спрайт
останавливается ЯВНО — Pixi крутит кадры сам, от общего тикера, и без
`sprite.stop()` картинка играла бы на замершем теле; на выходе `play()`
продолжает с того же кадра, `gotoAndPlay` был бы отменой).

Это ПАУЗА, а не отмена: замах, прерванный станом, после стана доигрывается и
бьёт, даже если игрок успел отойти — осознанное решение.

**Что выполняется ВСЕГДА, до заслона** (и почему):
- `poiseImmuneTimer` — `enemy.ts:289`, `boss.ts:317`. Иначе 2 секунды стана
  дарили бы цели 2 лишние секунды иммунитета к прерыванию, то есть iceball
  косвенно защищал бы цель от хитстана. Заодно у зверя декремент вышел
  из-под гейта "кадры зверя загрузились".
- Выталкивание игрока телом — `enemy.ts:299`, `boss.ts:325` (те же
  `pushPlayerOutOfEnemy`/`pushPlayerOutOfBoss`, что и в обычном кадре).
  Замороженная цель остаётся физическим телом: сквозь неё нельзя пройти.
  Идёт через `deps.pushPlayerOutX`, а это `pushPlayerOutXUnlessDashing` —
  значит рывок проходит сквозь тело и под станом тоже.

**Что заслон отключает намеренно** (знать при отладке): гравитацию —
застаненный в воздухе зависает до конца стана; и доигрывание
`hurtTimer`/`hitFlashTimer` — хитстан и вспышка от самого iceball
проигрываются ПОСЛЕ разморозки.

#### Память агро и режим расследования

Обе надстройки живут в обоих модулях по одной схеме, декремент — БЕЗУСЛОВНЫЙ,
до гейтов AI (`hurtTimer`/`windingUp` у зверя, `hurtTimer`+анимации атак у
босса), по той же причине, что и таймер стана.

- **Память агро** (`aggroMemoryTimer`, `AGGRO_MEMORY_MS` /
  `BOSS_AGGRO_MEMORY_MS`): условие агро считается каждый кадр и остаётся
  строгим (`enemy.ts:377`, `boss.ts:357`); пока оно выполняется, таймер
  взводится в полное значение (`enemy.ts:389`, `boss.ts:369`), перестало —
  тикает вниз, и всё это время цель считается агрённой. Нужна потому, что
  апекс прыжка героя выше допуска `SAME_FLOOR_TOLERANCE_TILES`, и без памяти
  враг терял цель на пол-прыжка. Поднимать сам допуск нельзя — на
  многоэтажных картах враг начал бы агриться сквозь пол.
- **Режим расследования** (`investigateX`/`investigateTimer`/
  `investigateLookTimer`, `INVESTIGATE_MS`/`INVESTIGATE_LOOK_MS`): получив
  урон вне агро, цель идёт к точке источника скоростью погони
  (`enemy.ts:456+`, `boss.ts:458+`), потом стоит паузу лицом к точке, потом
  возвращается к обычному поведению (зверь — патруль, босс — просто стоит).
  Ходьба заканчивается по любому из четырёх: дошёл, стена, край платформы,
  истёк таймер. Стена и край проверяются ТЕМИ ЖЕ функциями, что в патруле
  зверя (`isSolid` ×3 + `cellFootBlockTop`), своей геометрии нет. Обычное
  агро главнее: как только оно выполняется или жива его память, расследование
  сбрасывается целиком.
- Из этого следует, что "агрён" в коде обоих AI означает ИМЕННО память, а не
  сиюминутное условие, и что темп анимации ходьбы у зверя выбирается по
  ФАКТИЧЕСКОМУ шагу за кадр, а не по признаку агро (режимов движения три:
  погоня, ходьба расследования, патруль).

#### Урон и реакция на попадание — общие точки

- **`damageEnemy(enemy, amount, accumulator, sourceX)`** (`Explore.tsx:2490`)
  и **`damageBoss(amount, accumulator, sourceX)`** (`Explore.tsx:2529`) —
  единственные места, где списывается HP цели. Здесь же живут смерть,
  HP-бар, переход босса во вторую стадию и запуск расследования.
  `sourceX` — X ИСТОЧНИКА урона в мировых координатах, параметр
  ОБЯЗАТЕЛЬНЫЙ, без значения по умолчанию: молчаливая заглушка увела бы цель
  расследовать не туда, и заметить это в игре почти нельзя. Для меча, рывка
  и тика кровотечения это центр игрока, для взрыва снаряда — позиция
  СТРЕЛКА в момент выстрела (снаряд везёт её в себе), а не точка взрыва.
- **`applyEnemyHitReaction(enemy)`** (`Explore.tsx:2593`) и
  **`applyBossHitReaction(boss)`** (`Explore.tsx:2627`) — реакция цели на
  РАЗОВОЕ попадание: у зверя прерывание замаха с `POISE_POINT` и накопление
  `stunCount` → `POISE_IMMUNE_MS`, у босса два слоя (во время атаки/броска
  только вспышка `hitFlashTimer`, иначе хитстан/стан-резист). Вынесены из
  `applyAttackHit` без изменения логики и порогов.

Кто их зовёт — три источника, все только на НЕ смертельном попадании (гейт
по возврату damage-функции):

| Источник | Где |
|---|---|
| удар мечом | `Explore.tsx:2701` (враг), `2734` (босс) |
| взрыв снаряда fireball/iceball | `skills.ts:762` (враг), `775` (босс) |
| рывок dash | `skills.ts:891` (враг), `904` (босс) |

⚠️ **Тик кровотечения slash их НЕ зовёт НАМЕРЕННО.** Он идёт раз в секунду
пять секунд подряд, и хитстан держал бы цель в стан-локе весь этот срок.
Разовые попадания таким свойством не обладают — отсюда разница. Это
единственная причина, по которой встряска не встроена прямо в
`damageEnemy`/`damageBoss`.

⚠️ **КРИТИЧНО — порядок вызовов внутри тикера, менять нельзя** (номера строк
`Explore.tsx`, сверено):
```
skills.update(ticker.deltaMS)   :3201
enemySystem.update(dt, deltaMS) :3208
bossSystem.update(dt, deltaMS)  :3217
события (сундук/зелье/смуглер/обелиск) :3220+
анимации героя — там же applyAttackHit() :3443,
                 skills.onAttackStrike() :3448,
                 skills.onCastSpawnFrame() :3467
камера updateCamera(dt)         :3571
```
Внутри `bossSystem.update()` — тоже фиксированный порядок: **AI → шипы →
волны**. Ranged/stomp-ветки AI порождают снаряд/волну В ЭТОМ ЖЕ кадре
(`spawnBossSpike`/`spawnBossWave`) — блоки шипов/волн обязаны идти СРАЗУ
ПОСЛЕ AI, чтобы новорождённый снаряд получил первый шаг физики/hit-теста
сразу, а не на следующем кадре. По той же причине `updateProjectiles` внутри
`skills.update()` стоит ПОСЛЕ обработки нажатий, а урон рывка — после неё же.

⚠️ **`!` vs `?.` на вызовах systems — РАЗНОЕ и осознанное**:
`update()`/`spawn()` внутри тикера/`setup()` вызываются через `!`
(`enemySystem!.update(...)`, `bossSystem!.spawn(...)`) — там инвариант
"система уже создана" держится железно (создание — раньше первого вызова в
той же линейной `setup()`), и молчаливый пропуск через `?.` не нужен: если
он всё же нарушится, `!` уронит явную ошибку вместо тихого "враги просто
перестали двигаться". Но `dispose()` в CLEANUP эффекта — ЧЕРЕЗ `?.`
(`skills?.dispose()`): `setup()` асинхронный, а cleanup может сработать
РАНЬШЕ, чем системы созданы (React 19 StrictMode монтирует эффект дважды,
второй cleanup срабатывает почти сразу) — там инвариант НЕ держится. `!` на
`dispose()` уже один раз уронил белый экран (`Cannot read properties of
null (reading 'dispose')`) — обратно на `?.`, не трогать снова.

⚠️ **Особенность анти-стан-лока босса, перенесена как есть, не проверено,
задумана ли**: первый слой защиты (теперь он в `applyBossHitReaction`, а не
инлайн в `applyAttackHit`, как было при написании этой записи) проверяет
`boss.attackAnimPlaying || boss.rangedAnimPlaying`, но НЕ включает
`boss.stompAnimPlaying`. Если удар прилетает во время топота — код уходит в
слой 2 и МОЖЕТ выставить `boss.hurtTimer`, но в приоритете анимаций
